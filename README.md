# ue-ai-ops

> ★ **让 AI 能可靠地开发 Unreal Engine 工程的操作手册与工具集。**
> ★ 定位：**「工程操作层」** —— 不是「UE API 知识」（那些有专门的资料）。
> ★ 解决的问题：**代码写对了，但改不动 / 看不见 / 存不住。**
>
> ★★ **范围**：★ **只维护「本地实践」与「官方工具」两类内容** ——
> ★ **不收录针对某个具体第三方插件的补丁/分析**（那种内容的适用面窄、且随版本失效）。
>
> ★ **许可**：★ **双许可** —— ★ **脚本 MIT** · ★ **文档 CC BY 4.0**（见 `LICENSE`）。★ 即：脚本可随意集成（署名即可），文档可引用转载（注明来源即可）。
> ★ **免责**：本仓库为**独立整理的经验与文档**，★ 与 Epic Games 无隶属关系；
> ★ 引用 Unreal Engine 的公开文档与源码位置，★ **不包含其源代码的再分发**。

## 1. ★★ 两个最有价值的发现（先看这两条，能省很多时间）

### 1.1 ★★★ 官方已经内置了「AI 操控编辑器」的能力 —— 别自己造

★ **Unreal Engine 官方有一整套**（实测规模）：

| 组件 | 作用 | 规模 |
|---|---|---|
| Unreal MCP | MCP 服务端 | 105 文件 · 13k 行 |
| Toolset Registry | 工具集注册中心 | 145 文件 · 20k 行 |
| **All Toolsets** | ★ 一键启用全部工具集 | 依赖 20+ 工具集 |
| 工具集插件 | ★ **实测 50 个工具集** | 258 文件 · 43k 行 |
| AIAssistant | AI 助手本体 | 102 文件 · 16k 行 |
| ★ **合计** | —— | ★ **610 文件 · 92k 行** |

★★ **但它们全部默认不启用** ⇒ ★ **这就是「官方有 9 万行、却容易被漏掉」的根因。**

⇒ ★ **用之前先按 [`references/05`](references/05-official-mcp-and-toolsets.md) 启用**，
★ 并**先 `list_toolsets` 查官方有没有覆盖** —— ★ **有就别自己写。**

★ **抽样实测 5/5 全通**（含真读资产与控件树）→ [`references/06`](references/06-sampling-test-report.md)

### 1.2 ★★ 编译不必每次关编辑器

| 改动 | 能否不关编辑器 |
|---|---|
| ★ **只改 `.cpp` 函数体** | ✅ **能** —— 编辑器内按 **`Ctrl+Alt+F11`** |
| ★★ **改 `.h` 的反射**（`UPROPERTY` / `UCLASS` / 枚举，**哪怕只改名**） | ❌ **必须重启** |

★ **一句话判据**：★ **动 `.cpp` ⇒ 热重载；动 `.h` 反射 ⇒ 重启。**
★ 完整决策表 → [`references/01`](references/01-compile-and-launch.md)

## 3. 怎么用

### 3.1 装成 Agent skill（WorkBuddy 等）

```bash
# 把本仓库放进用户级 skill 目录
cp -r ue-ai-ops  <UserProfile>/.workbuddy/skills/ue-ai-ops
```

★ **skill 目录名与仓库名一致**（都叫 `ue-ai-ops`）——★ 一处改名、处处同名，不会有「仓库叫 A、skill 叫 B」的混淆。

★ **改完内容后同步**（★ 本仓库是**源**，skill 目录是**安装副本**）：
```bash
bash scripts/sync-to-skill.sh          # ★ 源 → skill 目录
```

★ 详见 [`INSTALL.md`](INSTALL.md)（含给别的开发者的分发方式与**验证方法**）。

### 3.2 手工用（不装 skill）

★ 直接读 `references/`；★ 用 `scripts/find-ue-editor-info.sh <工程目录>` 一键查当前状态。

## 4. ★★ 维护约定（★ 后续经验都写这里）

> ★ **本仓库是 UE 开发经验的唯一维护点。**
> ★ 项目里遇到新的 UE 经验 ⇒ ★ **提炼后写到这里**，项目侧只留**指路**。

### 4.1 往哪写

| 你有的东西 | 写到哪 |
|---|---|
| ★ **可复用的判据 / 决策表 / 做法** | ★ `references/NN-*.md`（手册） |
| ★ **实测记录 / 源码证据 / 排查链** | ★ `docs/evidence/`（证据） |
| ★ 一条独立的踩坑 | ★ `references/04-avoiding-pitfalls.md` |
| ★ 需要留档的改动（★ 不在版本控制里的） | ★ 写进对应的 `references/` 篇（★ 见 `references/04` §4·6） |
| ★ 官方工具集相关 | ★ `references/05-official-mcp-and-toolsets.md` |

### 4.2 ★★ 三条硬纪律

| # | 纪律 | 为什么 |
|---|---|---|
| 1 | ★★ **断言必须能指出来源**（官方文档 / 工具输出 / **推测**） | ★ 推的要标「未核实」—— ★ 否则会变成「假设的自我强化」（见 `references/04` §0） |
| 2 | ★★ **检查器必须带反向用例** | ★ 只报绿的检查器 = 没有检查器；★ **已实测被抓出过两次** |
| 3 | ★ **不含具体项目痕迹**（路径 / 端口 / 卡号） | ★ 写成「**怎么查**」而不是「查到的值」 ⇒ 换项目/换机器照样成立 |
| 4 | ★★ **不收「针对某个具体第三方依赖」的内容** | ★ 适用面窄、且**随那个依赖的版本失效** ⇒ ★ 若其中**有通用价值的部分**，★ **中性化后**再收（去掉具体名字，只留做法） |
| 5 | ★★ **改名 / 改结构时，先分清「活文档」与「历史记录」** | ★ **活文档**（手册 · 装法 · 脚本 · 台账）⇒ **必须同步改**；★ **历史记录**（评估 · 复盘 · 当时的实测）⇒ ★ **不该改**（改了反而失真，★ 它就该记「当时是什么样」） |

### 4.3 改完的验证

```bash
bash scripts/check.sh          # 通用性检查 + 结构检查
bash scripts/sync-to-skill.sh  # 同步到 skill 目录
```
