# 02 · 编辑器 MCP 通道（让 AI 操控编辑器）

> ★ 本文只讲★ **通道怎么建起来、怎么确认能用**。
> ★ **有哪些工具、怎么调** → 属于「连接器/工具清单」那一层（各家客户端不同）。

---

## 1. ★ 先分清三层（★ 混了就debug 半天）

```
① AI 客户端（WorkBuddy / Claude Code / Cursor …）
        ↕  协议层：MCP over stdio | HTTP | 原生 socket
② ★ 桥 / 连接器（可能独立进程，也可能就是客户端的一部分）
        ↕
③ ★ 编辑器内插件（★ 跑在编辑器进程里）
        ↕
   UE 编辑器：资产 · 关卡 · PIE · 日志
```

★ **最关键的结构性事实**：
> ★★ **③ 在编辑器进程内 ⇒ ★ 关掉编辑器，通道就没了。**
> ⇒ ★ **「AI 连不上编辑器」的第一嫌疑永远是：★ 编辑器没开。**

★ **① 与 ② 的形态**（★ 决定你该怎么查端口）：

| 形态 | 怎么发现端口 |
|---|---|
| HTTP 服务 | `netstat` 找 `LISTENING` 的固定/配置端口 |
| ★ **原生 socket，端口交给 OS** | ★ **端口每次启动都变** ⇒ ★ **只能从日志里读**（见下） |

---

## 2. ★★ 端口：必须从日志读，别信文档

### 2.1 为什么文档/记忆里的端口会过期

★ **三类坑**：

| 坑 | 表现 |
|---|---|
| ★ **端口常量是 0** | ★ 0 = **让操作系统随机分配** ⇒ ★ 每次启动都不同 ⇒ ★ 文档里记的旧值必然失效 |
| ★ **两个插件名字极像但不是同一个** | ★ 一个走随机 socket，另一个走固定 HTTP 端口（★ 实证：两者端口与协议都不同）⇒ ★ **连不上时先确认「我连的是哪个」** |
| ★ **配置改了但没生效** | ★ 自启开关通常**只在模块初始化那一刻读一次** ⇒ ★ **改完必须重启编辑器** |

### 2.2 ★ 正确的查法

```bash
# ① 先看插件自己报了什么（★ 权威来源是插件的日志，不是配置文件）
grep "port\|listening\|Assigned" <Project>/Saved/Logs/<Project>.log | tail -20

# ② 确认它真的在监听，且 PID 是编辑器进程
netstat -ano | grep -i LISTENING
tasklist | findstr UnrealEditor
```

★ **判别纪律**：
> ★ **「会不会监听」看 `netstat`，不看配置文件里写了什么。**
> ★ **「监听在哪个端口」看插件日志，不看文档、不看记忆。**

### 2.3 三层检查清单

| # | 检查 | 怎么查 | 缺了会怎样 |
|---|---|---|---|
| ① | ★ **编辑器在运行** | `tasklist` 有 `UnrealEditor` | 通道根本不存在 |
| ② | ★ **端口在监听** | `netstat -ano \| grep <端口>` → `LISTENING` | 连不上 / 超时 |
| ③ | ★ **PID 对得上** | ② 里的 PID == 编辑器 PID | ★ **连到了别的服务**（★ 最隐蔽的一种） |
| ④ | ★ **协议对得上** | ★ 插件是 HTTP 还是原生 socket？ | ★ HTTP 探原生 socket ⇒ 拿到 404 或空响应 |
| ⑤ | ★ **客户端信任了本地连接器** | 客户端侧的自定义连接器设置 | 连接被拒 |

★ **⑤ 是客户端侧的事**：★ 若①②③④都正常但连不上 ⇒ ★ **去客户端的连接器管理里看「信任」状态**。

## 3. ★ 启动参数的优先级

| 方式 | 做法 | 可靠性 |
|---|---|---|
| ★ **命令行参数** | `UnrealEditor.exe <uproject> -ModelContextProtocolStartServer` | ★ **高**（强制自启，不看设置） |
| 项目设置里开自启 | 设置项里把自启开关置 true | ★ **中**（★ 改完要重启才生效） |

★ **建议默认用命令行参数** —— ★ **它绕过了「设置有没有被读到」这个不确定性**。

★ **顺带**：很多插件还支持「自动编译」「持续编译」类参数/设置，★ 查引擎源码里该插件的
`AppSettings`/`Config` 命名，能找到全部可调项及其默认值（★ 比文档全）。

---

## 4. ★ 连不上时的排查树（★ 按顺序，别跳步）

```
AI 报「连不上 / 超时 / 空响应」
│
├─ 1. 编辑器在跑吗？
│     └─ 没跑 ⇒ 启动它（带 -ModelContextProtocolStartServer）★ 到此结束
│
├─ 2. 端口在监听吗？（netstat）
│     └─ 没监听 ⇒ ★ 看编辑器日志里插件有没有「Successfully initialized」
│           └─ 没有 ⇒ 插件没加载/没起 ⇒ 查插件是否启用、是否报加载错
│
├─ 3. 端口对吗？（★ 必须是本次启动的端口）
│     └─ 用了旧值 ⇒ ★ 去日志里读当前值
│
├─ 4. PID 对得上吗？
│     └─ 对不上 ⇒ ★ **连到了别的服务**（★ 同机有其它服务占这个端口）
│
├─ 5. 协议对吗？
│     └─ 用 HTTP 探一个原生 socket ⇒ ★ 必然失败（404 / 空 / 连接重置）
│           ⇒ ★ 换对协议再试
│
└─ 6. 客户端信任了吗？
      └─ ①②③④⑤ 都正常 ⇒ ★ 去客户端侧加信任
```

★ **不要跳步直接从「重启电脑」开始** —— ★ 上面六步覆盖了绝大多数情况。

## 4·5、★★★ 「端口通了」之后还有一道：★ **握手是有会话态的**

★ 走到上一步第 3 步（端口有东西应答）就宣布「通了」⇒ ★ **你会得到一个假绿**。
★ 实测过一次真实的踩坑：**探针一路 200，到最后一步全被拒**，而根因只有一个头没带。

### 4·5·1 ★★ 最该记住的一条

> ★★ **`initialize` 回 `200` 不等于握手成功。**

★ MCP 的 HTTP 传输里有一个**会话头**（如 `Mcp-Session-Id`）：

| 环节 | ★ 必须做的事 |
|---|---|
| `initialize` | ★ 从**响应头**里把会话头**取出来**（★ 不在响应体里） |
| 之后**每一个**请求 | ★ **原样回带**这个头 |
| 漏带的症状 | ★ 服务端日志打 `Missing required Mcp-Session-Id header` 之类，★ 客户端收 **400** |

★★ **阴险之处**：★ **漏带会话头时，`initialize` 本身照样回 `200`** ——
⇒ ★ 只看第一步的状态码 ⇒ ★ **必然误判成「通了」**，然后卡在后面 inexplicable 的 400 上。

★ **同类的第二道**：★ 握手完成后通常还要发一条 `initialized` 通知才真正生效（★ 回 `202` 才正常）。

### 4·5·2 ★★ 判据要**分层**，每层写清「不该出现什么」

★ 分层判据的好处是★ **可证伪** —— 每层都能独立指出「我坏在哪一步」：

| 层 | 动作 | ★ 正常长相 | ★ 不该出现（= 什么坏了） |
|---|---|---|---|
| L1 | 裸探一下（不带协议） | ★ `405`（★ 端点在，只是方法不对） | ★ **200** 反而可疑（★ 说明它不是只收 POST 的那类端点） |
| L2 | 握手第一步 | ★ `200` **且响应头里有会话头** | ★ `200` 但**没会话头** ⇒ ★ 后面全会 400 |
| L3 | 通知「已初始化」 | ★ `202` | ★ 报错 ⇒ ★ 会话头多半没带对 |
| L4 | ★ **列出工具** | ★ ★ **真拿到工具列表** ★ | ★ 空 ⇒ ★ 插件没启用 / 注册表没刷新 |

★★ **判据只能取 L4**：★ 前三层都是「准备工作」，★ **只有「真的列出了东西」才叫通**。

★ **可直接跑**：`scripts/mcp-session-probe.py`（★ 零依赖标准库，★ 端点可用 `--url` 或环境变量传）
```bash
python scripts/mcp-session-probe.py
python scripts/mcp-session-probe.py --expect-tools 3   # ★ 数量不符就非零退出（★ 适合进门禁）
```
★ 它的每条诊断行都带「★ 下一步该干什么」⇒ ★ **不是只报错码**。

★ **顺带**：★ 官方 MCP 通道**只暴露 3 个「元工具」**（`list_toolsets` / `describe_toolset` / `call_tool`）
⇒ ★ **「工具列表里没有我要的那个」往往是设计使然，不是故障**（★ 见 `05-official-mcp-and-toolsets.md` §4）。

### 4·5·3 ★ 「AI 客户端里看不到工具」的三种原因（★ 先分类，别急着修）

★ 排查半天发现**通道根本没坏** —— ★ 实际是这三类之一：

| # | 原因 | 判据 | 怎么办 |
|---|---|---|---|
| 1 | ★ **工具集代理设计**（★ 最常见） | ★ `tools/list` **只有 3 个元工具** | ★ **不是故障** ⇒ ★ 走「先列工具集 → 描述 → 调用」三步 |
| 2 | ★ **客户端连接器把空列表缓存了** | ★ 手写探针**能**列出工具，★ 但客户端里看不到 | ★ **重连/重启客户端**；★ 或★ **脚本自己做握手**（★ 零依赖可绕） |
| 3 | ★ 真的握手没完 | ★ 探针**也**停在某一层 | ★ 照 §4·5·2 逐层查 |

★★ **一条元纪律**（★ 本仓反复吃的那类亏）：
> ★ **「AI 调不到」和「工具不存在」是两个结论** —— ★ 中间隔着「客户端缓存」与「代理设计」两层。
> ⇒ ★ 宣布「官方没这个能力」之前，★ **先拿一份绕开客户端的独立证据**（★ 脚本握手就是那份证据）。

★ **为什么要留一个「绕开客户端的探针」**：
| 好处 | 说明 |
|---|---|
| ★ **排除客户端** | 分清「服务端没有」与「客户端没显示」 |
| ★ **可进门禁** | 命令有退出码 ⇒ 能当 CI 判据 |
| ★ **换客户端不失效** | ★ 客户端会换、会缓存、会抽风；★ 协议不会 |

## 5. ★ 能力边界：通道通了 ≠ 能干所有事

| 能做（典型） | 不一定行 |
|---|---|
| 建/改资产与控件 · 读资产树 · 跑 PIE · 读日志 | ★ **改 WBP 的「模板属性」可能不落盘**（见 `03-umg-and-assets.md`） |
| 查引擎反射信息 | ★ **触发重编译 / 改 UHT 产物**（★ 仍走 `01` 的编译流程） |
| 读蓝图结构 | ★ **任何要 UHT 重跑的事** |

★ **一句话**：★ **通道是「操控编辑器」，不是「替代编译流程」** ——
★ 改反射类的东西，通道再通也得走「关编辑器 → 编译 → 重开」。

## 6. 跨机器移植（★ 换项目/换人时）

★ **不要把这些写进长期文档**（★ 下表左列全是**反面教材** —— ★ 它们看着「具体」很好，★ 换台机器就全是错的）：

| ✗ 别写 | ✓ 写成 |
|---|---|
| 「端口是某个具体数字」 | 「★ 端口是随机分配的 ⇒ ★ 从 `<Project>/Saved/Logs/*.log` 里 grep `port`」 |
| 「引擎在某盘某具体版本目录」 | 「★ 引擎根 = 含 `Engine/Binaries/` 与 `Engine/Source/` 的目录」 |
| 「我项目的 uproject 在 X」 | 「★ `<Project>/<ProjectName>.uproject`」 |

★ **理由**：★ 具体值一换机器就错 ⇒ ★ **而「怎么找」永远成立**。
