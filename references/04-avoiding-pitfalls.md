# 04 · 避坑总表（★ 三次同族错误的血泪）

> ★ 本文只收★ **可迁移的判据**。★ 凡具体项目/路径/编号，一律不写。

---

## 0. ★★★★ 比「查不到」更隐蔽的一层：**假设的自我强化**

★ 本手册把这条放在**最前面** —— 因为它比 §1 更隐蔽、也更危险。

★ **三种错法，危险度递增**：

| | 错法 | 危险度 |
|---|---|---|
| ★ 常见 | 查了，但**查错地方** ⇒ 误判「不存在」 | 中 |
| ★★★ 更隐蔽 | ★ **根本没查 —— 自己推测一个机制，当成事实用** | ★ 高 |
| ★★★★ 最危险 | ★★ **把这个推测写进多份文件 ⇒ 靠「重复出现」获得可信度** | ★ **最高** |

★★ **实测案例**（一次完整的自我闭环）：

```
1) 我推测「记忆文件超过平台给的字数就会被截断」
2) ★ 把这个推测写进 3 个文件（记忆 / 坑清单 / 索引）
3) ★★ 之后引用时，看到的是「多处都这么写」
4) ★★★ ⇒ 它在我认知里【变成了事实】，并据此设计了一整套治理方案
5) 被追问「这个上限是谁定的」——★ 才发现：数字是平台给的，
   ★★ 而「会截断」是我【自己编的】
```

★★★ **两条铁律**：

> ★ **① 给「机制 / 阈值 / 必然发生」下断言时，必须能指出来源** ——
> 是官方文档写的？工具告诉你的？★ 还是**你自己推的**？
> ★ **推的就必须标「未验证」。**

> ★ **② 假设写进文件后会「自我强化」** ——
> ★ **越多人（或越多次）引用它，它越像事实。**
> ★ **别让未验证的假设以「多处一致」的方式获得可信度。**

★ **怎么破**：★ 凡带「限制 / 阈值 / 必然」性质的陈述，旁边标一行：
```
★ 来源：<官方文档 / 工具输出 / 推测>
★ 核实：已核实 / 未核实（★ 未核实的不作为硬约束）
```

★ **配套的可证伪检查**：★ **若某个「限制」真的存在，应该能观察到它的后果。**
★ 本例反证：★ **文件曾达 9,729 字符（远超所设的 3,000）而内容仍可被完整引用**
⇒ ★ **「会截断」不成立**。

## 1. ★★★ 第一条：「查不到」≠「不存在」

★ **这是本手册最重要的一条**，★ 也是 AI 最容易犯的错（★ 表现为「自信地给出错误结论」）。

### 1.1 实测的三次

| # | 我怎么查的 | 我的结论 | 真相 | 正解 |
|---|---|---|---|---|
| 1 | grep 组件的头文件没找到某方法 | 「这 API 是幻觉」 | ★ 它在★ **基类** 上 | ★ **让编译器说** |
| 2 | 换个类再 grep 一次 | 又判幻觉 | ★ 它在★ **兄弟类** 上（不是父子） | ★ **让编译器说** |
| 3 | ★ grep 资产二进制找控件名 | 「资产是空壳」 | ★ **控件名与图节点名不在同一张名字表** | ★ **用编辑器工具读真源** |
| ★4 | ★ **没读项目自己的文档就宣布「这是新发现」** | ★ 「这是新发现，没人做过」 | ★ **项目文档里早就详细记过了**（含每个工具集的用途） | ★ **先搜本仓 `docs/` 与历史记录** —— ★ **别把「我不知道」当成「没人知道」** |

### 1.2 为什么会犯

★ **三个错误有同一个结构**：
> ★ **「我查的那个地方没有」** ⇒ ★ 我当成 **「它不存在」**。

★ 而这两个之间隔着：
- ★ **继承链**（基类、兄弟类）
- ★ **多种存储**（同一份资产里有多张名字表）
- ★ **多层间接**（配置 → 生成物 → 运行时）

### 1.3 ★ 铁律

> ★ **判「某物不存在」之前，先问：「我查的地方，是不是它真正住的地方？」**
>
> ★ **grep / 正则只能证明「我查的地方没有」，不能证明「它不存在」。**

### 1.4 ★ 判据优先级（★ 从高到低）

| 优先级 | 来源 | 为什么 |
|---|---|---|
| ★ **1** | ★ **工具 / 编译器报错** | ★ 它真的读过代码/数据，★ 不会「看错地方」 |
| 2 | ★ **权威真源**（编辑器读出的结构、日志里插件自报的端口） | ★ 第一手的 |
| 3 | 引擎/框架源码 | ★ 需注意继承链与多份存储 |
| 4 | 官方文档 | ★ 可能过时、★ 可能记的是另一个组件 |
| 5 | ★ **模型记忆** | ★ ★ **最不可靠**（★ 名字记错、版本记混、★ 幻觉 API） |

★ **实战做法**：★ **当「记忆」与「工具报错」冲突时，永远信工具**；★
★ 且★ **把结论落成可复跑的命令**（★ 下次不用重新猜）。

## 2. ★ 编译错误的分类（★ 「没有错误」也是一类）

| 现象 | 分类 | 怎么处理 |
|---|---|---|
| ★ 有 `error C####` | ★ **真代码错** | ★ 照它说的改（★ 它精确到文件行号） |
| ★★ **一个 `error C` 都没有，但构建失败** | ★ **环境/流程问题** | ★ **看 `Result:` 那行的措辞**（★ 如「被 Live Coding 占用」「需要重启」） |
| ★ 构建「成功」但行为是旧的 | ★ **产物没更新** | ★ 比对★ **产物时间戳 vs 源码时间戳** |

★ **第 2 条最容易误判成「我代码写错了」** ⇒ ★ **判据：有没有 `error C`？**

★ **第 3 条的坑**：★ 「命令跑了」≠「编过了」——★ 内存不足/并发受限时可能中途失败而退出码仍为 0。

## 3. ★ 三个「同名不同物」（★ 排查时高频）

★ **通用规律**：★ **名字相似的两个东西，往往不是同一个。** 实测三类：

| 同名对 | 怎么区分 |
|---|---|
| ★ **两个插件端口服务** | ★ 看**插件自己日志里报的端口**，★ 别用文档里的旧值；★ 并核对 **PID 是不是目标进程** |
| ★ **两个同名指标/字段**（如大小写不同） | ★ 以★ **本项目/本工具的当前版本**为准 |
| ★ **「旧名兼容槽」与真实字段同名** | ★ ★ **这类是自找的坑**（★ 见下） |

★ **自造兼容槽的坑**（★ 实测）：
> ★ 保留「旧字段名」做向后兼容 —— ★ **但新代码里已经把字段改成新名了**
> ⇒ ★ **两个 UPROPERTY 声明同名** ⇒ ★ 反射层报错/行为异常。
> ★ **判据**：★ 改名后★ **搜一遍有没有留下同名的第二个声明**。

## 4. ★ 压缩/整理类操作的固有风险

★ **压缩文档、合并条目、重写配置**时，★ **「看起来等价」但实际丢了东西**是常态。

| 风险 | 表现 |
|---|---|
| ★ **静默丢判据** | ★ 压掉了某条约定，★ **没人发现，直到出事** |
| ★ 数值/单位变化 | 改写时把「72 字节」写成「72 字符」⇒ ★ **两端行为分叉** |
| ★ 注释自称与实际不符 | 注释说「与服务端一致」，★ 实际口径不同 ⇒ ★ **比没有文档更坏** |

★ **两个必备动作**：
1. ★ **关键项做存活核对**：★ 列一份「★ 这些必须还在」清单，压缩后逐条 grep
2. ★ **让检查器能抓到丢失**：★ 写一个**判据脚本 + 反向用例**（★ 故意删掉一项，检查器必须报红）

★ **反向用例是唯一能证伪「检查器真的在干活」的办法** ——
★ ★ **一个永远报绿的检查器，等于没有检查器。**

## 4·5、★★★ 一次真实的「判据过宽」事故（★ 本节是活体标本）

★ **事件经过**（2026-10-02 亲历）：

| 步 | 发生了什么 |
|---|---|
| 1 | 我给「记忆文件」写了个**容量门禁**，加了一条判据：★ **单条 ≤300 字符**（绝对阈值、无条件生效） |
| 2 | ★ **总量才用 53%** 时，一条 371 字符的条目照样被判「失败」 |
| 3 | ★★ 为了满足它，我**反复压缩、改写条目** |
| 4 | ★★★ **压缩过程中压丢了一条关键判据**（一个协议口径）—— 靠「关键判据存活」检查才发现 |
| 5 | ★ 使用者指出「**没必要这么严格**」⇒ 复查后确认：★ **这条判据是坏的** |
| 6 | ★ 修正为**条件判据**：★ **只在总量 ≥70% 时**才拦超长条目；充裕时只提示 |

★★★ **为什么这条判据坏**：★ 它犯了「**过宽 → 误报**」——
★ **一个「预算还很充裕」的文件，被一条与超载无关的规则判失败**。

★★★ **更重要的教训**（★ 这才是本节的价值）：
> ★ **误报不只是「烦」—— 它会逼人做坏事。**
> ★ 我为了消掉那个误报，去做了**本来不该做的压缩**，★ 而压缩**真的丢了信息**。
> ⇒ ★★ **一条过宽的判据，会主动制造它本想防止的损害。**

★★ **判据设计的两条原则**（★ 从这次事故总结）：
1. ★ **阈值要能说得清来源** —— ★ 别拍脑袋定「300」；
   ★ 改成比值（「一条不该独占预算的 1/6 以上」）就能说清了。
2. ★ **相对量优先于绝对量** —— ★ 问「**它占了多少预算**」，而不是「它有多长」。

★ **改完必须跑反向用例**（★ 否则分不清「改对了」还是「改松了」）：

| 用例 | 期望 |
|---|---|
| ★ **预算充裕 + 超长条目** | ★ **只提示，不失败** |
| ★ **预算吃紧（≥70%）+ 超长条目** | ★ **失败** |
| ★ **总量超上限** | ★ **失败** |

★ 实测三条**全部符合预期** ⇒ ★ **是「改对了」，不是「改松了」**。

★ **延伸判据**：★ **任何「自动阻断」类检查，都要能回答「它拦住的是不是真问题」** ——
★ 拦不住的（漏报）会**静默放行**，★ 拦多了的（误报）会**逼人绕过或破坏**。

## 4·6、★ 改动要能「独立移交」

★ **凡是改了「不在你版本控制里」的东西 ⇒ 必须留下可重放的说明。**

| 为什么 | 说明 |
|---|---|
| ★ **不在版本控制里** | 改了也不会被 git 记录 ⇒ ★ **换机器/换人就没了** |
| ★ 编辑器内改动 | 资产被 ignore / 是二进制 ⇒ ★ 同样查不到改了什么 |
| ★ 环境级改动 | 设置、插件、注册项 ⇒ ★ 最容易「只有我这台机器是对的」 |

★ **留档要写清四样**：

| # | 内容 | 为什么 |
|---|---|---|
| 1 | ★ **精确位置**（哪个文件 / 哪一行 / 插什么） | ★ 换版本时能快速重新定位 |
| 2 | ★ **文件指纹**（哈希） | ★★ **指纹不符 ⇒ 版本变了 ⇒ 别照抄行号** |
| 3 | ★ **验证命令与判据** | ★ 「改完了」要靠命令证明，不是靠感觉 |
| 4 | ★ **怎么回滚** | ★ 改坏了要能退回去 |

★★ **一条常被忽略的原则**：
> ★ **不要为了容纳自己的改动去改别人的约定** ——
> ★ 例如「把某个被 ignore 的目录纳入版本控制」。
> ★ 那往往是**有理由的既有决定** ⇒ ★ **用留档解决，而不是改规则。**

## 4·7、★★★ 停用/注释代码时，**别去改「调用点那一行」**

★ **一条被同一种坑咬过三次才总结出来的原则。**

### 4·7·1 ★ 三次同类事故（★ 都是「改边界、破坏配对结构」）

| # | 做了什么 | 后果 |
|---|---|---|
| 1 | ★ 注释掉 `if (X)` **那一行**，但留下了 `{ }` 和函数体 | ★ `C2059: 语法错误:"）"` |
| 2 | ★ 注释 `UPROPERTY` 声明行时**只改了一半**（改了注释文案、没停用声明） | ★ `C2065: 未声明的标识符` |
| 3 | ★ 注释「调用某函数的那一行」—— ★ **行尾的 `}` 跟着被注释掉了** | ★★ `C2601: "xxx": 本地函數定義` **×10** |

★★ **共同点**：★ 被注释的那一行**往往同时承载结构符号**（`{` `}` `;`），
★ 而它**看起来只是一行**。

### 4·7·2 ★★ 正确做法：**改「被调用方」，不改「调用点」**

```cpp
// ✗ 错：去注释调用点 —— 每处都要处理结构，还容易漏
    if (TitleText) { TitleText->SetFontSize(72);
//  ApplySpacing(TitleText, ...); }        ← ★ 行尾的 } 一起没了

// ✓ 对：改被调用方 —— ★ 一处改动、结构完全不动、一行即回滚
    auto ApplySpacing = [](UTextBlock* Text, float Spacing)
    {
        return;                            // ★ 临时停用就加这一行
        ...
    };
```

★ **为什么更好**：
| 优点 | 说明 |
|---|---|
| ★ **一处 vs 多处** | ★ 9 处调用只需改 **1 个地方** |
| ★ **不碰结构** | ★ 不动任何 `{ } ;` ⇒ ★ **不会破坏配对** |
| ★ **回滚就是删一行** | ★ 排查完删掉 `return;` 即可 |
| ★ **意图清晰** | ★ 一眼看出「这里被临时停用了」 |

### 4·7·3 ★ 配套的可复跑自检：**大括号配平**

★ 改完先跑一次，**比等编译器快得多**：

```python
import io, re
s = io.open(<file>, encoding="utf-8").read()
s = re.sub(r"//[^
]*", "", s)                    # 去行注释
s = re.sub(r"/\*.*?\*/", "", s, flags=re.S)       # 去块注释
s = re.sub(r'"(?:[^"\]|\.)*"', '""', s)     # 去字符串
print(s.count("{"), s.count("}"))                 # ★ 两数必须相等
```

★ **判据**：★ **`{` 数 == `}` 数**。★ 不等 ⇒ ★ **别急着编译**（★ 一编就是十几个连锁错误）。

## 4·8、★★★ 「调用返回成功」≠「事情做成了」

★ 这是本仓最贵的一类坑：★ **不崩、不报错、有返回码，于是所有人都当它成了**。

### 4·8·1 三种「静默失效」的样子

| # | 形态 | ★ 典型场景 |
|---|---|---|
| 1 | ★ **设了不支持的属性** | ★ 给一个**类型上就没有该字段**的对象设值 ⇒ 返回成功、实际丢弃 |
| 2 | ★ **缓存了空结果** | ★ 客户端连接器在服务端就绪前初始化 ⇒ 之后一直显示「无工具」 |
| 3 | ★ **量错了对象** | ★ 拿「含背景的整体」当元素尺寸 ⇒ 数字看着有值、其实偏了一圈 |

★ **共同点**：★ **每一种都能靠「读回来 / 绕开一层 / 换测量对象」当场识破** ——
★ ★ **所以它们全都不是「无法发现」，而是「没人去发现」**。

### 4·8·2 ★ 对策只有一条纪律

> ★★ **凡「写操作」，必须配一条「读回来」。**

| # | 反面 | ★ 正面 |
|---|---|---|
| 1 | 设完就往下走 | ★ **设完立刻读回同一处，比对** |
| 2 | 「跑完了」= 成功 | ★ **让脚本报 `ok / fail`；★ `fail≠0` 就算整批失败** |
| 3 | 「看起来对就行」 | ★ ★ **量 / 截图 / 读属性**（★ 「看着对」是最不可复跑的判据） |
| 4 | 只信客户端显示 | ★ ★ **另找一条绕开客户端的独立证据**（★ 脚本握手、命令行、文件 mtime） |

★ **第 4 条的由来**：★ 一次「官方工具调不到」的排查里，
★ **服务端完全正常（脚本握手四层全过）、只有客户端侧看不到** ——
⇒ ★ **若当时没有那条独立证据，就会去改本来没坏的插件。**

### 4·8·3 ★★ 假绿的两种「配方」（★ 亲手各犯过一次）

★ **第 3 种形态（量错对象）已见 §3·5·3**（★ 那是在被测对象之外的另一类）。
★ 下面两条是**同一类病的两种配法**，★ 都不是「写错了」，★ 是「**报告与事实脱钩**」：

| 配方 | ★ 症状 | ★ 修法 |
|---|---|---|
| ★ **带白名单的通配符** | ★ 拷贝/清理用了 `*.某扩展名` ⇒ ★ 新增另一种扩展名的文件被静默漏掉 | ★ **别按扩展名白名单搬文件**；★ 要么全搬，要么显式列出 |
| ★ **报告只统计成功那部分** | ★ 报告数字来自「刚拷成功的东西」⇒ ★ ★ **漏了几个永远显示不出来** | ★ ★ **报告要拿「源」与「目标」两个数对比**（★ 不一致就失败退出） |

★★ **这两个配方叠在一起 = 必假绿**（★ 一个负责漏、一个负责掩盖漏）。
★ 实测经过：新增一个 **`.py`** 脚本后，跑同步脚本报告「scripts/ 3 个」★ **一切正常** ——
★ 而副本里**根本没有那个新脚本** ⇒ ★ **AI 侧继续用旧知识，且没有任何报错**。

> ★★ **一条可推广的纪律**：★ **任何「我加了 X」的动作，判据不能是「脚本跑完了」，
> 而必须是「从目的地侧重新清点 X 在不在」。**

## 4·9、★★★ 「输入喂进去了、日志全对、值纹丝不动」—— ★ 引擎在**当帧末尾**把那个量清零

★ **场景**：不走轴映射，而是**在代码里逐帧算出增量、手动喂给引擎的「累加型」输入接口**
（★ 转视角、俯仰、移动输入都属这一类）。

★ **症状**（★ 最难查的那种）：诊断日志证明**每一步都跑了、数值也算对了**，
★ 但被驱动的那个量**一动不动**。

★★ **根因**：这类量往往是「**累加 → 同一帧里被取走消费 → 消费完清零**」的一次性缓冲。
★ 写入点若落在**取走的那一步之后**，★ **当帧就作废** —— 下一帧读到的还是 0。

```bash
# ★ 怎么查（★ 别猜，直接看那个类的 Tick 实现）
grep -n "RotationInput" Engine/Source/Runtime/Engine/Private/PlayerController.cpp
grep -n "void APlayerController::TickActor" -A 12 Engine/Source/Runtime/Engine/Private/PlayerController.cpp
grep -n "void APlayerController::UpdateRotation" -A 6 Engine/Source/Runtime/Engine/Private/PlayerController.cpp
```

★ 读出来的顺序是：**`PlayerTick()`（内含取走那个缓冲的一步）→ `Tick()` → ★ 缓冲被清零**。
★ **来源**：★ 引擎源码（UE 5.8）· ★ 行号随版本变 ⇒ ★ **用上面的 grep 现跑，别记顺序细节**。
★ ★ **本条的启示**：★ 源码路径**也要核实** —— ★ 本节初稿把文件写成 `…/Private/GameFramework/PlayerController.cpp`
★ （★ 因为同目录确实有一堆 `GameFramework/` 的文件），★ 实际它在 `Private/` **根下** ⇒ ★ 命令一跑就暴露。
★ **写进文档的每条命令，都该当场跑一次**（★ 见本文 §1.4 判据优先级 —— ★ 工具输出高于记忆）。

★★ **做法**：★ 覆写**取走之前的那个函数**，★ 把喂入放在 `Super` **之前**：

```cpp
void AMyPlayerController::PlayerTick(float Delta)
{
    FeedInputsManually();      // ★ 必须在 Super 之前
    Super::PlayerTick(Delta);  // ★ 这里面把输入取走、并在末尾清零
}
```

★ **推广成一条判据**（★ 比本例大得多）：

> ★★ **凡是「往引擎持有的累加器里写值」，先去源码找三个点：★ 谁读它 · 什么时候读 · 读完清不清。**
> ★ **清零点决定写入点。** ★ 找不到这三个点就动手 ⇒ ★ 你会得到一个「日志全对」的死循环。

★ **同族识别法**：★「**日志证明逻辑跑过了**」≠「**数据被消费了**」——
★ 这两件事之间隔着**引擎的调用顺序**，★ 而日志永远看不见它。

## 4·10、★★ 「注入类工具」必须**双向对账**（★ 回执成功 ≠ 进了被测应用）

★ **场景**：用**系统级输入模拟**（键盘 / 鼠标注入）驱动正在运行的游戏或编辑器，★ 以此验证某个行为。

| # | 坑 | 表现 |
|---|---|---|
| 1 | ★ **回执只说明「系统接走了」** | ★ 返回值非 0 就宣布「事件已送达」；★ 实际焦点、权限、窗口层级任一不对都能把它吞掉 |
| 2 | ★ **结构尺寸不对 ⇒ 整批被拒** | ★ 注入用的结构里那个联合体**只声明了一个分支** ⇒ ★ `sizeof` 比系统期望的小 ⇒ ★ **返回 0、一条都不投递**（★ 它报的是「参数不对」，★ 不是「权限不够」，★ 所以很容易往错方向查） |
| 3 | ★ **「发了」当成「做了」** | ★ 于是「行为没出现」被解释成「功能没生效」，★ 回头去改本来没坏的代码 |

★ **两条正解**：

1. ★ **发之前先自证结构尺寸**：★ 打印 `sizeof` 与该平台的约定值比对
   （★ Windows 的输入事件结构是 **40 字节**，★ 鼠标 / 键盘 / 手柄**三个分支都要在联合体里声明齐**）。
2. ★★ **要一条「能独立证明刺激进了被测应用」的证据** ——
   ★ 首选**让被测程序自己在输入处理处打日志**；★ 次选换一种**能直接改变应用可见状态**的刺激
   （★ 例如真实移动光标位置，★ 看应用读到的坐标有没有跟着走）。

★★ **判据**：★ **注入 API 的返回值只当「操作系统收到了」，绝不当「被测应用收到了」。**
★ **对账 = 发出侧计数 ＋ 接收侧日志**，★ 两边都对上才叫「输入生效」。

★ **与 §4·8 的关系**：★ 同族，★ 但这里的失败发生在 **OS 与目标进程之间** ——
★ 「读回来」在这里读不到（★ 那不是一条属性），★ 所以只剩**双向对账**这一条路。

## 4·11、★ **采样周期必须显著短于被测事件时长**（★ 否则「已经做完」会被读成「没发生」）

★ **场景**：用远程调用（★ 一次请求一个来回）逐帧观察一个**很短**的事件 —— 跳跃、受击、一帧内的清零、过场。

★ **实测的错法与代价**：★ 单次远程调用往返 **2~4 秒**，★ 而被测事件只持续 **0.8 秒** ⇒
★ 所有样本都落在事件**结束之后** ⇒ ★ 结论写成「没生效」，★ 还顺手"修"了一遍本来正常的代码。

| 做法 | 说明 |
|---|---|
| ★ **复用同一条会话** | ★ 握手只做一次，★ 之后在**自己的循环里**连续调用（★ 几十 Hz），★ 不是每帧重连一次 |
| ★ **先问时长、再定采样率** | ★ 判据：**★ 采样间隔 ≤ 事件时长的 1/5**；★ 达不到就别用它当判据 |
| ★ **看序列形状，不看单点** | ★ 例：抛物线（★ 峰值 ＋ 回落）才是「跳了」的证据；★ 一个静止值证明不了任何事 |

★★ **一句话**：★ **「读回来全平」≠「没发生」**（★ 与 §4·8 同族 —— ★ 那一节是「写进去没生效」，
★ 本节是「发生了没读到」）。

## 4·12、★★ 给应用**绑键**之前，先确认这颗键**能到应用**

★ **实测**：在编辑器里跑「游戏内会话」（PIE）时，★ 某些键**根本不会送到游戏**：
★ ① ★ **窗口 / 编辑器层先截走**；★ ② ★ 截走之后还**直接结束整个会话**（★ 游戏侧一条日志都收不到）。
★ ⇒ 表现为「我按了、游戏毫无反应」，★ 极容易被误判成「我的绑定写错了」。

★★ **两步前置检查**（★ 绑任何键之前都该跑）：

| 步 | 做什么 | 判据 |
|---|---|---|
| 1 | ★ **空按一次**（★ 功能还没写） | ★ 被测程序的日志**有没有收到这颗键**（★ 收到才说明通道在） |
| 2 | ★ **确认它有没有别的副作用** | ★ 会不会关掉会话 / 窗口（★ 会 ⇒ ★ 这颗键不能用，★ 换一颗） |

★ **避坑清单**：★ 编辑器与系统保留的那几颗（★ 关闭 / 退出 / 撤销一类）**默认别绑**；
★ 若「最自然的那颗」恰好被占，★ **在代码注释里写明「为什么用这颗、不用那颗」** ——
★ 否则后来的人一定会来问「为什么不直接用退出键」。

★ **同一族的第二种**：★ **鼠标点击** —— ★ 界面上「看得见」的控件**不一定吃得到命中测试**
（★ 父级可见性设成「画出来但不参与命中」时，★ **绘制与命中就分家了**）。
★ ⇒ ★ **每个交互件各自留一次「真的被点到」的日志**，★ 别用「看起来在」推断「能点」。

## 4·13、★★ 「这个做不到」要么有源码依据、要么别说 —— ★ 去读那条链路的**入口函数**

★ **场景**：被要求「不按任何键、只要移动鼠标就转视角」。★ 直觉上有两种反应，★ **都不对**：
★ 「当然可以啊」（★ 然后花三小时换捕获档位，★ 全无效）；★ 或「这不可能」（★ 但说不清为什么）。

★★ **正解是去读实现**：★ 标准鼠标轴的链路里，★ **视口只在「已经捕获」时才累加鼠标 delta**，
★ 而「捕获」的**唯一入口是按下鼠标** ⇒ ★ 在标准轴链路上这件事**结构上做不到**。

```bash
# ★ 一个 `if` 就是全部答案（★ 实测于 UE 5.8）
grep -n "FSceneViewport::OnMouseMove" -A 16 \
  Engine/Source/Runtime/Engine/Private/Slate/SceneViewport.cpp
```

★ **来源**：★ 引擎源码 · 视口的鼠标移动处理函数（★ 里面那个「视口是否已捕获」的判断）。

★ 于是把**两个可行方案与各自代价**摆出来**让人裁定**，★ 而不是自己挑一个闷头做：

| 方案 | 得到 | 代价 |
|---|---|---|
| ★ **点一下抓指针**（★ 切到「只给游戏」的输入模式） | ★ 增量真实进来、★ 可无限旋转 | ★ 光标被锁在中心并隐藏 ⇒ ★ **界面上的按钮点不着** |
| ★ **自己量光标的屏幕位移**逐帧换算 | ★ 界面照常可点、★ 手感是「移动就转」 | ★ 光标会撞屏幕边界 ⇒ ★ **到边就转不动**（★ 绝对坐标天生有界） |

★★ **两条附带判据**：

1. ★ **别把两条转视角的路叠起来**（★ 同一个量被喂两次 = 双倍速度且不可解释）。
   ★ 本例可以**天然互斥**，★ 不用加开关位：★ 抓指针时让它在**捕获瞬间隐藏光标**，
   ★ 于是按住那一刻起光标被按回原位 ⇒ ★ 自量那条自己归零。
   ★ **来源**：★ 输入模式的捕获选项（★ 源码里有这个开关）＋ ★ 机制推断；
   ★ **未单独实测过"归零后的数值"** —— ★ 用它之前先自己确认一次「按住期间自量那条的增量确实 ≈ 0」。
2. ★ **「到边转不动」是「量的类型」问题，不是「灵敏度」问题** ——
   ★ 绝对坐标有边界、★ 增量没有；★ 先分清手上量的是哪种，★ 再决定是调常数还是换通道。

★ **推广**：★ **可行性问题不要靠「应该可以吧」回答。** ★ 去读那个事件的**入口函数**，
★ 看它有没有条件分支挡着 —— ★ **一个 `if` 就值三小时。**

## 4·14、★★★ **换控制方案 = 换观测定义**（★ 老判据不会报错，★ 它只会一直给你错的东西）

★ **场景**：把「角色永远面向镜头前方」改成「角色转向自己移动的方向」。★ 改动本身只有两个开关，★
★★ 但**验证用的那套脚本一条都没改 ⇒ 它继续「成功」，而含义已经变了**：

| 改动前 | 改动后 |
|---|---|
| ★ actor 的 yaw **就等于**镜头 yaw | ★ actor 的 yaw = **身体朝向**；★ 镜头 yaw 只在控制器的转向属性里 |
| 判「鼠标转视角有没有生效」= 读 actor yaw | ★ 同一个读法**测的是另一件事了**（★ 数字照样漂亮） |

★★ **还有一层障碍**：★ 想改读那个控制器属性，★ 结果**远程工具读回来是空的**
（★ 结构体型属性读不出来）。★ **来源**：★ 工具实测 —— ★ 注意这不是「引擎里没有这个值」，
★ 而是「**这条通道拿不到**」（★ 见 §1 第一条：★ 查不到 ≠ 不存在）。

★ **替代判据怎么找**（★ 本例的解法，★ 值得抄）：★ 利用新行为本身 —— ★ 身体会**精确对齐**镜头方向，
★ 于是「**走一步，看身体落到哪个角度**」能把镜头 yaw **反推**出来；★ 顺带把更早标定的
★ 「多少像素对应多少度」**反向验回**了一遍（★ 推算值与实测落点分毫不差）。

★★ **纪律**：

> ★ **改动「由谁驱动某个量」时，同一次提交里必须重述一遍：★「我要看的到底是哪个数」。**
> ★★ **最危险的判据不是会失败的判据，而是换了含义还能返回数字的判据。**

★ **附带一条测量口径的坑**：★ 朝向 / 视效这类东西 ★ **别靠坐标系推导定案** ——
★ 实测里「正对还是背对」「上移还是下移」★ 两次推导都被**实拍**否掉，★ 最后靠两帧图定出偏移角，
★ 靠**真人手感**定出一个符号。★ **判据：★ 朝向看像素、手感问使用者，★ 推导只负责提出候选。**
★ （★ 同族见 `03-umg-and-assets.md` 的「导入外部模型」—— ★ 单位也是只能量、不能猜。）

## 4·15、★★ 打开「引擎自动帮你算」的开关之前，★ 先问：我的输入有没有依赖它算出来的那个量

★ **实测的连锁**（★ 两行配置引发的「按住侧移键 = 原地打圈」）：
★ 打开「角色转向移动方向」⇒ ★ 身体开始随移动向量转；
★ 而移动输入是**按 actor 自身的前 / 右向量**算的 ⇒ ★ 输入方向又随身体转 ⇒ ★★ **正反馈**。

★ **正解**：★ 输入基准换成**与被自动改动的那个量无关**的东西 —— ★ 本例＝用镜头朝向拍平成一个轴后取轴，★ 而不是 actor 的前 / 右向量。

| # | 判据 |
|---|---|
| 1 | ★ **成对的开关要一起验** —— ★ 「解耦控制器旋转」与「开启自动转向」★ 只设一个就是另一种病 |
| 2 | ★ **打开任何「自动帮我算 X」的开关，先列一张「谁在读 X」的清单** —— ★ 我的输入基准在不在里面 |
| 3 | ★ **别用「名字看起来正好」的便捷接口当基准** —— ★ 那个「基础瞄准朝向」看着正好等于「镜头方向」，★ 实际**返回值随谁在控制它而变**：★ 有控制器时给的是**视点 / 摄像机朝向**（★ 还掺着俯仰），★ **没有控制器时直接回落成 actor 自身朝向** ⇒ ★ 那条回落分支 ★ **正好把正反馈请回来** |
| 4 | ★ **转到位要多久是可调的**（★ 角速度常数）—— ★ 引擎默认值往往够用，★ 但要**显式写出来**并注明「这是选过的数」，★ 否则下一个人以为没人管过它 |

★ **核对命令**（★ 别信本条的措辞，★ 去读实现 —— UE 5.8 实测）：

```bash

grep -n "FRotator APawn::GetBaseAimRotation" -A 12 Engine/Source/Runtime/Engine/Private/Pawn.cpp
```
★ 读出来是两段：★ `有控制器 && 不在自由相机` ⇒ 返回 `GetPlayerViewPoint()` 的朝向；★ 否则 ⇒ `GetActorRotation()`。
★ **来源**：★ 引擎源码（★ 上面这条 grep）。

★ **推广**：★ **「两个各自合理、接在一起就打圈」的配置对，★ 是引擎自动化最常见的一类坑。**
★ 同类还有：★ 自动对齐 ＋ 自己写的插值、★ 自动重力 ＋ 自己写的落地判定。

## 4·16、★ **验证脚本自己也会造假** —— ★ 这回是**假红**

## 6. ★★ 最后一条元纪律

★ **第 4 次的变体（★ 更隐蔽）**：
> ★ **不是「查不到」，而是「根本没查」** —— ★ **把「我不知道」当成了「别人也不知道」**。
> ⇒ ★ **宣布「这是新发现 / 没人做过」之前，必须先搜**：★ **本仓 `docs/` · 历史记录 · 官方文档站**。

★ **AI 写下的每个结论，都要能回答一个问题：「你怎么知道的？」**

★★ **加问一句：「这个依据本身核实过吗？」** —— ★ 引用一个**未核实的假设**，和直接编造一样危险（★ 而且更难发现，因为「看起来有出处」）。

★ **答不上来 ⇒ 标成「未验证」，不要写成断言。**

★ **实测收益**（★ 亲历）：
