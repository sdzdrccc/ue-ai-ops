# 04 · 避坑总表（★ 三次同族错误的血泪）

> ★ 本文只收★ **可迁移的判据**。★ 凡具体项目/路径/编号，一律不写。

---

## 0. ★★★★ 比「查不到」更隐蔽的一层：**假设的自我强化**

★ 本手册把这条放在**最前面** —— 因为它比 §1 更隐蔽、也更危险。

★ **三种错法，危险度递增**：

| | 错法 | 危险度 |
|---|---|---|
| ★ 常见 | 查了，但**查错地方** ⇒ 误判「不存在」 | 中 |
| ★★★ 更隐蔽 | ★ **根本没查 —— 自己推测一个机制，当成事实用** | ★ 高 |
| ★★★★ 最危险 | ★★ **把这个推测写进多份文件 ⇒ 靠「重复出现」获得可信度** | ★ **最高** |

★★ **实测案例**（一次完整的自我闭环）：

```
1) 我推测「记忆文件超过平台给的字数就会被截断」
2) ★ 把这个推测写进 3 个文件（记忆 / 坑清单 / 索引）
3) ★★ 之后引用时，看到的是「多处都这么写」
4) ★★★ ⇒ 它在我认知里【变成了事实】，并据此设计了一整套治理方案
5) 被追问「这个上限是谁定的」——★ 才发现：数字是平台给的，
   ★★ 而「会截断」是我【自己编的】
```

★★★ **两条铁律**：

> ★ **① 给「机制 / 阈值 / 必然发生」下断言时，必须能指出来源** ——
> 是官方文档写的？工具告诉你的？★ 还是**你自己推的**？
> ★ **推的就必须标「未验证」。**

> ★ **② 假设写进文件后会「自我强化」** ——
> ★ **越多人（或越多次）引用它，它越像事实。**
> ★ **别让未验证的假设以「多处一致」的方式获得可信度。**

★ **怎么破**：★ 凡带「限制 / 阈值 / 必然」性质的陈述，旁边标一行：
```
★ 来源：<官方文档 / 工具输出 / 推测>
★ 核实：已核实 / 未核实（★ 未核实的不作为硬约束）
```

★ **配套的可证伪检查**：★ **若某个「限制」真的存在，应该能观察到它的后果。**
★ 本例反证：★ **文件曾达 9,729 字符（远超所设的 3,000）而内容仍可被完整引用**
⇒ ★ **「会截断」不成立**。

## 1. ★★★ 第一条：「查不到」≠「不存在」

★ **这是本手册最重要的一条**，★ 也是 AI 最容易犯的错（★ 表现为「自信地给出错误结论」）。

### 1.1 实测的三次

| # | 我怎么查的 | 我的结论 | 真相 | 正解 |
|---|---|---|---|---|
| 1 | grep 组件的头文件没找到某方法 | 「这 API 是幻觉」 | ★ 它在★ **基类** 上 | ★ **让编译器说** |
| 2 | 换个类再 grep 一次 | 又判幻觉 | ★ 它在★ **兄弟类** 上（不是父子） | ★ **让编译器说** |
| 3 | ★ grep 资产二进制找控件名 | 「资产是空壳」 | ★ **控件名与图节点名不在同一张名字表** | ★ **用编辑器工具读真源** |
| ★4 | ★ **没读项目自己的文档就宣布「这是新发现」** | ★ **项目文档里早就详细记过了**（含每个工具集的用途） | ★ **先搜本仓 `docs/` 与历史记录** —— ★ **别把「我不知道」当成「没人知道」** |

### 1.2 为什么会犯

★ **三个错误有同一个结构**：
> ★ **「我查的那个地方没有」** ⇒ ★ 我当成 **「它不存在」**。

★ 而这两个之间隔着：
- ★ **继承链**（基类、兄弟类）
- ★ **多种存储**（同一份资产里有多张名字表）
- ★ **多层间接**（配置 → 生成物 → 运行时）

### 1.3 ★ 铁律

> ★ **判「某物不存在」之前，先问：「我查的地方，是不是它真正住的地方？」**
>
> ★ **grep / 正则只能证明「我查的地方没有」，不能证明「它不存在」。**

### 1.4 ★ 判据优先级（★ 从高到低）

| 优先级 | 来源 | 为什么 |
|---|---|---|
| ★ **1** | ★ **工具 / 编译器报错** | ★ 它真的读过代码/数据，★ 不会「看错地方」 |
| 2 | ★ **权威真源**（编辑器读出的结构、日志里插件自报的端口） | ★ 第一手的 |
| 3 | 引擎/框架源码 | ★ 需注意继承链与多份存储 |
| 4 | 官方文档 | ★ 可能过时、★ 可能记的是另一个组件 |
| 5 | ★ **模型记忆** | ★ ★ **最不可靠**（★ 名字记错、版本记混、★ 幻觉 API） |

★ **实战做法**：★ **当「记忆」与「工具报错」冲突时，永远信工具**；★
★ 且★ **把结论落成可复跑的命令**（★ 下次不用重新猜）。

## 2. ★ 编译错误的分类（★ 「没有错误」也是一类）

| 现象 | 分类 | 怎么处理 |
|---|---|---|
| ★ 有 `error C####` | ★ **真代码错** | ★ 照它说的改（★ 它精确到文件行号） |
| ★★ **一个 `error C` 都没有，但构建失败** | ★ **环境/流程问题** | ★ **看 `Result:` 那行的措辞**（★ 如「被 Live Coding 占用」「需要重启」） |
| ★ 构建「成功」但行为是旧的 | ★ **产物没更新** | ★ 比对★ **产物时间戳 vs 源码时间戳** |

★ **第 2 条最容易误判成「我代码写错了」** ⇒ ★ **判据：有没有 `error C`？**

★ **第 3 条的坑**：★ 「命令跑了」≠「编过了」——★ 内存不足/并发受限时可能中途失败而退出码仍为 0。

## 3. ★ 三个「同名不同物」（★ 排查时高频）

★ **通用规律**：★ **名字相似的两个东西，往往不是同一个。** 实测三类：

| 同名对 | 怎么区分 |
|---|---|
| ★ **两个插件端口服务** | ★ 看**插件自己日志里报的端口**，★ 别用文档里的旧值；★ 并核对 **PID 是不是目标进程** |
| ★ **两个同名指标/字段**（如大小写不同） | ★ 以★ **本项目/本工具的当前版本**为准 |
| ★ **「旧名兼容槽」与真实字段同名** | ★ ★ **这类是自找的坑**（★ 见下） |

★ **自造兼容槽的坑**（★ 实测）：
> ★ 保留「旧字段名」做向后兼容 —— ★ **但新代码里已经把字段改成新名了**
> ⇒ ★ **两个 UPROPERTY 声明同名** ⇒ ★ 反射层报错/行为异常。
> ★ **判据**：★ 改名后★ **搜一遍有没有留下同名的第二个声明**。

## 4. ★ 压缩/整理类操作的固有风险

★ **压缩文档、合并条目、重写配置**时，★ **「看起来等价」但实际丢了东西**是常态。

| 风险 | 表现 |
|---|---|
| ★ **静默丢判据** | ★ 压掉了某条约定，★ **没人发现，直到出事** |
| ★ 数值/单位变化 | 改写时把「72 字节」写成「72 字符」⇒ ★ **两端行为分叉** |
| ★ 注释自称与实际不符 | 注释说「与服务端一致」，★ 实际口径不同 ⇒ ★ **比没有文档更坏** |

★ **两个必备动作**：
1. ★ **关键项做存活核对**：★ 列一份「★ 这些必须还在」清单，压缩后逐条 grep
2. ★ **让检查器能抓到丢失**：★ 写一个**判据脚本 + 反向用例**（★ 故意删掉一项，检查器必须报红）

★ **反向用例是唯一能证伪「检查器真的在干活」的办法** ——
★ ★ **一个永远报绿的检查器，等于没有检查器。**

## 4·5、★★★ 一次真实的「判据过宽」事故（★ 本节是活体标本）

★ **事件经过**（2026-10-02 亲历）：

| 步 | 发生了什么 |
|---|---|
| 1 | 我给「记忆文件」写了个**容量门禁**，加了一条判据：★ **单条 ≤300 字符**（绝对阈值、无条件生效） |
| 2 | ★ **总量才用 53%** 时，一条 371 字符的条目照样被判「失败」 |
| 3 | ★★ 为了满足它，我**反复压缩、改写条目** |
| 4 | ★★★ **压缩过程中压丢了一条关键判据**（一个协议口径）—— 靠「关键判据存活」检查才发现 |
| 5 | ★ 使用者指出「**没必要这么严格**」⇒ 复查后确认：★ **这条判据是坏的** |
| 6 | ★ 修正为**条件判据**：★ **只在总量 ≥70% 时**才拦超长条目；充裕时只提示 |

★★★ **为什么这条判据坏**：★ 它犯了「**过宽 → 误报**」——
★ **一个「预算还很充裕」的文件，被一条与超载无关的规则判失败**。

★★★ **更重要的教训**（★ 这才是本节的价值）：
> ★ **误报不只是「烦」—— 它会逼人做坏事。**
> ★ 我为了消掉那个误报，去做了**本来不该做的压缩**，★ 而压缩**真的丢了信息**。
> ⇒ ★★ **一条过宽的判据，会主动制造它本想防止的损害。**

★★ **判据设计的两条原则**（★ 从这次事故总结）：
1. ★ **阈值要能说得清来源** —— ★ 别拍脑袋定「300」；
   ★ 改成比值（「一条不该独占预算的 1/6 以上」）就能说清了。
2. ★ **相对量优先于绝对量** —— ★ 问「**它占了多少预算**」，而不是「它有多长」。

★ **改完必须跑反向用例**（★ 否则分不清「改对了」还是「改松了」）：

| 用例 | 期望 |
|---|---|
| ★ **预算充裕 + 超长条目** | ★ **只提示，不失败** |
| ★ **预算吃紧（≥70%）+ 超长条目** | ★ **失败** |
| ★ **总量超上限** | ★ **失败** |

★ 实测三条**全部符合预期** ⇒ ★ **是「改对了」，不是「改松了」**。

★ **延伸判据**：★ **任何「自动阻断」类检查，都要能回答「它拦住的是不是真问题」** ——
★ 拦不住的（漏报）会**静默放行**，★ 拦多了的（误报）会**逼人绕过或破坏**。

## 4·6、★ 改动要能「独立移交」

★ **凡是改了「不在你版本控制里」的东西 ⇒ 必须留下可重放的说明。**

| 为什么 | 说明 |
|---|---|
| ★ **不在版本控制里** | 改了也不会被 git 记录 ⇒ ★ **换机器/换人就没了** |
| ★ 编辑器内改动 | 资产被 ignore / 是二进制 ⇒ ★ 同样查不到改了什么 |
| ★ 环境级改动 | 设置、插件、注册项 ⇒ ★ 最容易「只有我这台机器是对的」 |

★ **留档要写清四样**：

| # | 内容 | 为什么 |
|---|---|---|
| 1 | ★ **精确位置**（哪个文件 / 哪一行 / 插什么） | ★ 换版本时能快速重新定位 |
| 2 | ★ **文件指纹**（哈希） | ★★ **指纹不符 ⇒ 版本变了 ⇒ 别照抄行号** |
| 3 | ★ **验证命令与判据** | ★ 「改完了」要靠命令证明，不是靠感觉 |
| 4 | ★ **怎么回滚** | ★ 改坏了要能退回去 |

★★ **一条常被忽略的原则**：
> ★ **不要为了容纳自己的改动去改别人的约定** ——
> ★ 例如「把某个被 ignore 的目录纳入版本控制」。
> ★ 那往往是**有理由的既有决定** ⇒ ★ **用留档解决，而不是改规则。**

## 4·7、★★★ 停用/注释代码时，**别去改「调用点那一行」**

★ **一条被同一种坑咬过三次才总结出来的原则。**

### 4·7·1 ★ 三次同类事故（★ 都是「改边界、破坏配对结构」）

| # | 做了什么 | 后果 |
|---|---|---|
| 1 | ★ 注释掉 `if (X)` **那一行**，但留下了 `{ }` 和函数体 | ★ `C2059: 语法错误:"）"` |
| 2 | ★ 注释 `UPROPERTY` 声明行时**只改了一半**（改了注释文案、没停用声明） | ★ `C2065: 未声明的标识符` |
| 3 | ★ 注释「调用某函数的那一行」—— ★ **行尾的 `}` 跟着被注释掉了** | ★★ `C2601: "xxx": 本地函數定義` **×10** |

★★ **共同点**：★ 被注释的那一行**往往同时承载结构符号**（`{` `}` `;`），
★ 而它**看起来只是一行**。

### 4·7·2 ★★ 正确做法：**改「被调用方」，不改「调用点」**

```cpp
// ✗ 错：去注释调用点 —— 每处都要处理结构，还容易漏
    if (TitleText) { TitleText->SetFontSize(72);
//  ApplySpacing(TitleText, ...); }        ← ★ 行尾的 } 一起没了

// ✓ 对：改被调用方 —— ★ 一处改动、结构完全不动、一行即回滚
    auto ApplySpacing = [](UTextBlock* Text, float Spacing)
    {
        return;                            // ★ 临时停用就加这一行
        ...
    };
```

★ **为什么更好**：
| 优点 | 说明 |
|---|---|
| ★ **一处 vs 多处** | ★ 9 处调用只需改 **1 个地方** |
| ★ **不碰结构** | ★ 不动任何 `{ } ;` ⇒ ★ **不会破坏配对** |
| ★ **回滚就是删一行** | ★ 排查完删掉 `return;` 即可 |
| ★ **意图清晰** | ★ 一眼看出「这里被临时停用了」 |

### 4·7·3 ★ 配套的可复跑自检：**大括号配平**

★ 改完先跑一次，**比等编译器快得多**：

```python
import io, re
s = io.open(<file>, encoding="utf-8").read()
s = re.sub(r"//[^
]*", "", s)                    # 去行注释
s = re.sub(r"/\*.*?\*/", "", s, flags=re.S)       # 去块注释
s = re.sub(r'"(?:[^"\]|\.)*"', '""', s)     # 去字符串
print(s.count("{"), s.count("}"))                 # ★ 两数必须相等
```

★ **判据**：★ **`{` 数 == `}` 数**。★ 不等 ⇒ ★ **别急着编译**（★ 一编就是十几个连锁错误）。

## 5. ★ 日常自检（★ 每条都可复跑）

| # | 判据 | 命令/做法 |
|---|---|---|
| 1 | ★ 编译真的过了 | `grep "Result:" build.log` + 比对产物与源码时间戳 |

| 7 | ★ 文档表格没写坏 | ★ 表格单元格内**不能出现竖线**（★ 转义也不行）⇒ 会把表拆错列 |

★ **第 7 条**：★ Markdown 表格里为了写正则常带 `|`，★ **那会被当成列分隔符** ⇒ ★ **把命令放到表格外面**。

## 6. ★★ 最后一条元纪律

★ **第 4 次的变体（★ 更隐蔽）**：
> ★ **不是「查不到」，而是「根本没查」** —— ★ **把「我不知道」当成了「别人也不知道」**。
> ⇒ ★ **宣布「这是新发现 / 没人做过」之前，必须先搜**：★ **本仓 `docs/` · 历史记录 · 官方文档站**。

★ **AI 写下的每个结论，都要能回答一个问题：「你怎么知道的？」**

★★ **加问一句：「这个依据本身核实过吗？」** —— ★ 引用一个**未核实的假设**，和直接编造一样危险（★ 而且更难发现，因为「看起来有出处」）。

★ **答不上来 ⇒ 标成「未验证」，不要写成断言。**

★ **实测收益**（★ 亲历）：
| 我原本的断言 | 实际 | 代价 |
|---|---|---|
| 「编译必须关编辑器」 | ★ 有热重载这条路 | ★ 每次多花 3–5 分钟重启 |
| 「改资产属性不落盘」 | ★ 是「不自动保存」 | ★ 差点改错工具设计方向 |
| 「这个资产是空壳」 | ★ 有 44 个控件 | ★ 差点推倒重来 |

★★★ **三次都是「没验证就下结论」。⇒ ★ 代价不是「错一次」，★ 是「按错的方向做了一整轮」。**
