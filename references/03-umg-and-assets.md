# 03 · UMG 界面与资产（★ 架构判据 + 落盘根因）

> ★ 本文讲★ **界面代码怎么组织**、★ **资产类操作为什么会「改了没生效」**。

---

## 1. ★★ 核心架构判据：WBP 只做布局

> ★★ **WBP（Widget Blueprint）只负责「控件的位置、尺寸、层级、名字」；
> ★ 逻辑、静态文案、样式值、事件绑定 ★ 全部放 C++。**

| 放哪 | 具体内容 |
|---|---|
| ★ **WBP** | 控件布局 · 控件**名字**（C++ 按名字取） |
| ★ **C++** | ★ 静态文案 · ★ 颜色/尺寸常量 · `OnClicked` 等事件 · 数据显示与填充 · 提示条内容 |

### 1.1 ★ 为什么样式值必须放 C++

★ **亲历的三种返工**：

| 返工 | 表现 |
|---|---|
| ★ **「两处都写」** | 同一个颜色在 C++ 和 WBP 各写一遍 ⇒ ★ 改了一处忘了另一处 ⇒ ★ 长期不一致 |
| ★ **「资产里改不到 / 改不持久」** | ★ 见 §3 ⇒ ★ 最后只能改 C++，等于白在资产里试 |
| ★ **「无法 review」** | ★ 样式值在二进制资产里 ⇒ ★ **代码 review 看不见、回归测试跑不到** |

★ **推论**：★ **凡是「每个项目都要、且要能 review」的东西 ⇒ 放代码；★ 凡是「每个项目都不一样、且靠美术手感」的东西 ⇒ 放资产。**

### 1.2 ★ 绑定写法

| 写法 | 行为 | ★ 建议 |
|---|---|---|
| ★ `BindWidget` | ★ 找不到该控件 ⇒ **直接加载失败** | ✗ **不用**（★ 会毁掉「C++ 当空壳跑流程」的退路） |
| ★ `BindWidgetOptional` | 找不到 ⇒ **置 null，不报错** | ✅ **用这个**（★ 功能照走，缺控件只影响那一处） |

★ **事件绑定**：★ 用普通委托（`AddDynamic` / `AddUObject`）——
★ **不要用 UMG 的 Property Binding**（★ 那是蓝图里把属性拖成绑定 / C++ 里每帧反射取值）。

★ **判定命令**（搜到即违规，`BindWidget` 本身不算）：
```bash
grep -rnE "Bind\(&|CreateBinding|PropertyBinding" <Module>/Private/UI/
```

★ **自查小技巧**：★ 在 C++ 里留一条**启动日志**，逐个打印绑定是否成功 ——
★ 「控件没接上」是静默的（不崩、只是没效果），★ **日志能把它变成可见的**。

## 2. ★ 改 WBP 之前：先拿真源

★ **两种错误做法**：
| ✗ 做法 | 为什么错 |
|---|---|
| ★ **猜控件名** | 猜错 ⇒ 绑定为 null ⇒ ★ **静默无效果**，你以为是代码问题 |
| ★ ★ **直接 grep 资产二进制** | ★ **资产里有多张名字表**（图节点、控件、资源…）⇒ ★ **grep 只能命中其中一张** ⇒ ★ 会得出「资产是空的」这种★ **完全错误的结论**（★ 实测栽过） |

★ **正确做法**：★ **用编辑器工具读控件树**（不同客户端工具名不同，功能都是「读当前资产的结构」）：
```
选中资产 → 设为目标 → 读控件树
```
★ 拿到 ★ **真实控件名 + 层级 + 类型**，★ 再决定对齐方向。

### 2.1 ★ 对齐方向：先定一条，别混

| 方向 | 做法 | 何时选 |
|---|---|---|
| ★ **改代码对齐资产** | 保留 WBP，把 C++ 的绑定名改成与它一致 | ★ **资产已经做得不错**（★ 风险最低：资产不动） |
| 改资产对齐代码 | 重命名 WBP 控件 | ★ 代码名已对外（文档/团队约定），★ 且资产改动可控 |

★ **代价意识**：★ 改资产名可能**破坏已有布局与绑定** ⇒ ★ 改之前先备份/提交。

★ **混合方案**（两头都不放弃）：★ 代码里做一层**名字映射**（新名 → 旧名）——
★ 优点是两边名字都保住；★ 缺点是多一层映射、后续维护要记两套名。

## 3. ★★★ 「改了不落盘」：根因与修法

### 3.1 现象

★ **MCP 改控件属性** ⇒ 接口返回成功 ⇒ **立刻读回也对** ⇒ ★ **但资产文件 mtime 不动** ⇒ 关掉重开就丢了。

### 3.2 ★ 根因：三个调用分管三件事，前两个不管落盘

| 调用 | 作用 | 管落盘 |
|---|---|---|
| `Modify()` | ★ **撤销栈**（能不能 Ctrl+Z 退回） | ✗ |
| `MarkBlueprintAsStructurallyModified` | ★ 「蓝图变了，要重编译」 | ✗ |
| ★ `MarkPackageDirty()` | ★ 「这个包有未保存改动」 | ★ **这才是** |
| ★ 保存（如 `PromptForCheckoutAndSave`） | ★ **写磁盘** | ★ **这才是** |

★ **典型缺陷写法**：
```
写入属性 ✅
MarkBlueprintAsStructurallyModified ✅      ← 只管重编译
return success                                ← ★ 没标脏、没保存 ⇒ 调用方误以为「成功 = 已存」
```

### 3.3 ★ 修法（两层都要）

| 层 | 加什么 | 效果 |
|---|---|---|
| ★ **资产层** | 写操作后 `MarkPackageDirty()` | ★ 编辑器知道「有未保存改动」 |
| ★ **调用层** | 成功后**显式保存** | ★ **当场写磁盘**（★ 这才叫「改了就在」） |

★ **只加资产层不够** —— ★ **用户关掉编辑器照样丢。**

★ **关于「会不会弹窗」**：★ 保存接口常有多个参数控制（是否提示、是否可取消）——
★ **无人值守场景要显式关掉交互**，否则会卡在一个模态框上。

### 3.4 ★ 一分钟自查

```
改一个属性 → 立刻看资产文件的 mtime
   变了 ⇒ 落盘正常 ✔
   没变 ⇒ ★ 写入路径缺标脏/缺保存
```

★ **建议把这个检查写成一个脚本**（见 `../scripts/`）—— ★ **它能挡掉「以为成功了」这类静默失败**。

## 3·5、★★★ 几十个控件要改时：★ headless 批处理，别在编辑器里手点

★ 一次要改几十个控件（★ 批量套几何、批量改名、批量灌样式）⇒ ★ **逐个在编辑器里改 = 慢 + 不可复跑 + 会漏**。

★ **投递前两条硬闸**（★ 都属于「门禁全绿、其实没生效」那一族，★ 判据全文在 `04`，这里只指路）：
  · ★ **不能有 play session 在跑**（★ 会话期间改资产 ⇒ 崩溃报告 ＋ 一条保存通道假 `success` ＋
    ★ 之后新起的会话里那一屏根本不构造）⇒ **§4·22**；★ 顺序记一句：**拍 → 停 → 投 → 再拍**；
  · ★ **删件的那一轮，必须数「资产里有、投递意图里没有」是不是零条**
    （★ 同一个编辑器进程里「删掉重建」**不会清空旧树**，★ 加法看不出来、减法才暴露）⇒ **§4·21**。

### 3·5·1 ★ 姿势

```
★ 先导出一份「几何真源」（★ 样式/坐标从别处来，别手抄）
        ↓
★ 用无头编辑器跑一个脚本：读真源 → 逐控件灌值 → 标脏 + 保存
        ↓
★ 判据：脚本自己打印 ok=N fail=M   ★ M≠0 就当失败处理，别只看「跑完了」
```

★ **命令行形态**（★ 无需开着编辑器界面）：
```bash
<Engine>/Binaries/<Platform>/UnrealEditor-Cmd.exe <Project>.uproject \
  -run=pythonscript -script=<repo>/tools/<apply>.py \
  -stdout -unattended -nosplash -nullrhi
```
★ 关键参数：`★ -stdout`（★ **日志进 stdout，否则你什么都看不见**）· ★ `-nullrhi`（★ 不建渲染设备）· ★ `-unattended`（★ 不弹窗）。

### 3·5·2 ★★★ 写完必须「读回来」

★★ **本条是这一节的核心**，★ 也是最容易省掉、代价最大的一条：

> ★ **「设置属性的调用返回成功」≠「值真的写进去了」。**

★ 实测过的静默失效：**给一个不支持该属性的槽位设置它 ⇒ 返回成功、实际没写**。
★ 通用形态：★ **调用方只管「设了」，没人回读「到底生效没」**。

| # | 纪律 | 做法 |
|---|---|---|
| 1 | ★ **设完立刻读回** | ★ 同一个对象把属性读出来，比对；★ 不等就当没设 |
| 2 | ★ **数量对不上就失败** | ★ 打印 `ok / fail`；★ ★ **`fail≠0` ⇒ 整批算失败**（★ 别只看「跑完了」） |
| 3 | ★ **留几何证据** | ★ 改完**截图或量一次边距**（★ 「看着对」不算，见 §3·5·3） |

### 3·5·3 ★★ 两个「量出来才知道」的坑

| 坑 | 现象 | ★ 怎么抓 |
|---|---|---|
| ★ **渲染器裁掉一圈** | ★ 截图里底部/右侧少一截 | ★ ★ **截图尺寸 ≠ 视口尺寸**（★ 窗口边框/工具栏会吃掉一部分）⇒ ★ **要么显式设视口，要么截完按已知比例裁** |
| ★ **背景骗过自动测量** | ★ 量「卡片宽度」量出一个含背景的巨型数字 | ★ ★ **紧裁到元素边界再量**；★ ★ **带花纹/渐变的背景不能参与判边** |

★★ **这两条的共同教训**：
> ★ **自动测量只能量「边界干净的东西」。**
> ★ 一旦测量对象周围有装饰、背景、边框，★ **量出来的数一定偏向「包含它们的那个整体」**。

### 3·5·4 ★ headless 的四个坑（★ 实测，详见 `07`）

| 坑 | 症状 | ★ 避 |
|---|---|---|
| ★ 日志不落盘 | ★ 脚本 print 了但什么都没收到 | ★ 加 `-stdout` |
| ★ 输出被管道掐断 | ★ 处理到一半就死（★ 像是脚本崩了） | ★ ★ **别把长输出直接管到 `head`**；★ 先重定向进文件再看 |
| ★ 资产树不可直接写 | ★ 脚本报权限/受保护错误 | ★ 走编辑器给的接口改，不直接改资产对象 |
| ★ 传 JSON 字符串当参数 | ★ 参数被当成本体类型解析失败 | ★ **命令行传 JSON 要显式声明成字符串** |

★ **第 2 条特别阴**：★ **`head` 之类的工具提前关管道 ⇒ 读端一关 ⇒ 写进程被信号杀掉** ——
★ 表现像「脚本跑到一半崩了」，★ 实则是**你自己掐死了自己**。

## 4. 界面的其它常见决策

| 决策点 | 建议 | 理由 |
|---|---|---|
| ★ **要不要用 CommonUI** | ★ **界面少、单端输入时不要用** | 它为「面板堆栈 + 多端输入路由」而生 ⇒ 界面少时是过度设计 |
| ★ **要不要 WebUI（CEF）** | ★ **先别用** | 能 1:1 还原设计稿，但增包体/内存，★ 且有合规与性能成本 |
| ★ **渐变/模糊/外发光** | ★ **纯色降级优先**，真要效果再上材质 | ★ 渐变在 UI 里常用「贴图」实现 ⇒ ★ 没有美术资源时纯色最省 |
| ★ **固定比例适配** | ★ 设计期按目标分辨率写死，★ 运行时用等比缩放容器 | 避免「一堆绝对坐标在不同分辨率下全错位」 |
| ★ **字体** | ★ 先用引擎默认，★ 留好换装口子 | ★ 字体资源常缺；★ **字号全部走常量**，换字体只改一处 |

★ **共同点**：★ **以上都能「先降级、后补齐」** ⇒ ★ 别在资源没到位时卡住不动。

## ★★★ 批量建控件树时的三条硬约束（★ 2026-10-06 实测 · 一次真实的两屏施工）

> **场景**：用 `apply_layout` 一次性建 26~28 个控件的屏。★ 三条都是**「建完读回来」才发现的**
> —— ★ **不读回就会交付一个「看着建好了、实际文字全空」的界面**。

### ① ★★ **单内容槽控件放多个子 ⇒ 静默丢失**

| 控件 | 槽位 | 后果 |
|---|---|---|
| ★ **`UButton`** | `Content` **单槽** | 放两个子 → ★ **只留第一个，其余静默消失**（★ 实测：「‹ 图标 ＋ 返回」丢了「返回」） |
| ★ **`UBorder`** | `Content` **也是单槽** | ★ 同上（★ 实测：卡片里的「头像＋道号＋境界」三件丢了两件） |

★ **正解**：这类控件有 >1 个子时**自己套一层容器**：
- ★ `Button` ⇒ 套 **`HorizontalBox`**（典型是「图标 + 文字」横排）
- ★ `Border` ⇒ 套 **`CanvasPanel`**（典型是卡片内**绝对定位**的元素）

★ **判据**：★ **建完立刻 `get_widget_tree`，逐个数子控件** —— ★ 少一个都说明踩了这条。

### ② ★★ `Slot.Offsets.Right / Bottom` 是**宽 / 高**，不是右下角坐标

★ **实测**：写 `Offsets = {Left:-48, Top:-48, Right:432, Bottom:258}`（**以为是「右下角坐标」**）
⇒ ★ **读回 `Size = (432, 258)`**，而目标宽高是 **480×306** ⇒ ★ **尺寸全错**。

★ **正确语义**（`CanvasPanelSlot` · 单点锚时）：
```
Position = (Offsets.Left, Offsets.Top)      ← 相对锚点的偏移
Size     = (Offsets.Right, Offsets.Bottom)  ← ★ 就是宽高，不是坐标
```
★ **交叉印证法**：★ **拿一个「已知尺寸」的既有资产反推** ——
★ 找一个你**知道设计宽高**的控件（例如一张标注了宽度的卡片），看它的 `Offsets.Right`：
★ 若那个数**恰好等于它的宽**（而不是「左边距 + 宽」），★ 就一秒确认了本条的语义。
★ 这比读源码快，且**用的是你手上真实的数据**。

★ **拉伸锚**（`Anchors.Minimum != Maximum`）时，`Offsets` 才是**四边距**（全 0 = 铺满）。

### ③ ★★★ 控件要被 `BindWidget` 绑到，**必须勾 `Is Variable`**

★ **实测**：`apply_layout` / `create_widget` 建出来的控件 **`bIsVariable` 默认 `false`**
⇒ ★ **C++ 的 `BindWidgetOptional` 全部取到 `nullptr`**
⇒ ★★ **界面表现：布局全在、但文字一个都没有**（提示条、标题、按钮文案全空）★ **且不报错**。

★ **判据**：官方 MCP 的 `GetWidgets` 返回里每个控件都带 **`bIsVariable`** ⇒ ★ **逐个核**。
★ **修法**：官方 `UMGToolSet.ToggleWidgetAsVariable`（★ 注意 `widget` 的 refPath 形如
`/Game/UI/WBP_X.WBP_X:WidgetTree.<控件名>`）。

★★ **这是「假绿」的典型**：★ 「控件建出来了」与「控件能被 C++ 用上」是**两件事**
⇒ ★ 只看控件树会以为成功。

## ★★ 工具链两条通道的分工（★ 实测确认）

| 通道 | 协议 | 端口 | 独有能力 |
|---|---|---|---|
| **项目内 UMG MCP 插件**（如 `UmgMcp`） | ★ **原生 socket**（★ **不是 HTTP** —— `curl` 连不上） | ★ **OS 随机**（★ 从日志读 `Assigned unique listener port`） | ★ `apply_layout`（**批量建树**）· `save_asset` |
| **官方 `ModelContextProtocol`** | ★ **HTTP + SSE** | **8000**（`-ModelContextProtocolPort=N` 可改） | ★ **`set_parent`（设 WBP 父类）** · ★ **`ToggleWidgetAsVariable`** · `GetWidgets` · `CompileWidgetBlueprint` |

★★ **关键**：★ **设父类与设变量只有官方通道有** ⇒ ★ **两条互补，不是二选一**。
★ 新建的 WBP **父类默认是 `UserWidget`** ⇒ ★ 不设成自己的 C++ 屏类，`LoadClass` 会失败、
★ 退回 C++ 基类 ⇒ ★ **WBP 白建**（能编译、能落盘、但运行时根本不用它）。

★★ 官方通道是 **Tool Search 三件套**（`list_toolsets` / `describe_toolset` / `call_tool`）：
- ★ `call_tool` 的字段名是 **`tool_name`**（★ **不是 `name`**）
- ★ `tool_name` **不带 toolset 前缀**（`get_parent`），而 `describe_toolset` 返回的是**全限定名**
  ⇒ ★ 要剥掉前缀
- ★ 复杂参数**写进文件**用 `--args-file` —— ★ 在 shell 里手拼嵌套 JSON 会吃引号地狱

## ★★ 空 Brush 的 `UImage` 会画成**一块纯色**（默认白）

★★ **实测踩过**：新建的屏，`BG` 之类的背景 `Image` **没设贴图**（美术资源未到位）
⇒ ★ **整个界面是一片纯白** —— ★ 因为 `UImage` 在「没有 `ResourceObject`」时
**画的是「纯色填充」**，颜色由 **`ColorAndOpacity`** 决定，而它默认是 **(1,1,1,1)**。

★ **同一个坑的第二种表现**：屏上某处突然**多出一块白矩形**（本该是立绘 / 法阵 / 图标位）。

★ **正解**：★ **美术没到位时，每个占位 `Image` 都必须显式给色**：
| 用途 | 给什么 |
|---|---|
| ★ **背景层** | ★ **给底色**（把设计底色写进 `ColorAndOpacity`）—— ★ 否则整屏白 |
| ★ **装饰/占位层**（立绘位 · 法阵位 · 图标位） | ★ **`ColorAndOpacity` 的 A 设 0**（透明）—— ★ 干净地「留空」 |

★★ **不能指望「没图就不显示」** —— ★ **它会显示成一个白块**。

★ **连带的一条**：★ 有既有屏做参照时，★ **先照抄它同类控件的色值** ——
★ 本条的实例里，老屏的背景在布局文件里**显式写了墨色**所以没这个毛病，
★ 新屏漏了这一步才翻车。★ 判据：★ **新屏的背景控件，去老屏找同位置的那个控件、抄它的色。**

## ★★ 「控件建出来了」≠「界面有内容」——两种**表现相同、根因不同**的沉默失败

★ 都表现为「界面上**什么都没有**」，但：
| # | 根因 | 判据 |
|---|---|---|
| **A** | ★ 控件**没勾 `Is Variable`** ⇒ C++ 的 `BindWidget` 取到 `nullptr` ⇒ 逻辑完全没有作用对象 | ★ 读 `GetWidgets` 看每项的 **`bIsVariable`** |
| **B** | ★ 控件在、也能绑上，★ **但没人给它内容**（既没在代码里设、也没在资产里填） | ★ **逐个问**：这个控件的**内容来源**是什么？★ 代码设 / 资产填 / ★ **还是「本来就该空」** |

★★ **教训**：★ **「不参与逻辑」不等于「不需要内容」**。
★ 一个纯装饰的 `TextBlock`（字标 / 印章字 / 符号）**照样要有人写字** ——
★ 按「装饰类不绑」的原则跳过它，★ 结果就是那一处**永远空着**。

★ **交付前的检查法**：★ 把「C++ 绑定的控件清单」与「真的有内容来源的控件清单」**对一遍**，
★ **差集就是空的那些位置**。

## ★★★ 导入外部模型（FBX）：★ 单位、朝向、动画三件事都得「量 / 拍」，★ 一件都不能推

> **场景**：★ 拿到一个外部 DCC 导出的骨骼网格，★ 要挂到第三人称角色身上**替换占位几何体**。
> ★ 三条都是**"看着成功了、其实没对上"**那一族（★ 见 `04 §4·8`）。

### ① ★★ **单位在导入端就丢了** —— ★ 判据：**量它，不要猜它**

| 现象 | 说明 |
|---|---|
| ★ 资产读出来的包围盒是 `0.59` 这类数 | ★ 那**只是「单位」** —— ★ 不是米、★ 也不是厘米；★ 各家 DCC 的导出缩放约定互不相同 |
| ★ 于是「角色多高」没有权威值 | ★ 猜 1.7、★ 猜 170、★ 硬编码放大 150 倍 —— ★ 三种都会让★ **下一个读代码的人完全没法负责** |

★ **做法（★ 两步自标定，★ 只用引擎一定给对的那个空间）**：

1. ★ 先按缩放 `1.0` 挂上，★ 读**组件的世界包围盒** —— ★ 世界单位在引擎里就是厘米，★ 这个可信；
2. ★ 由「目标身高 ÷ 实测世界高度」算出缩放 ⇒ ★ **再量一次** ⇒ ★ 把包围盒最低点（脚底）压到碰撞胶囊底部。

```cpp
const FBoxSphereBounds Raw = Body->CalcBounds(Body->GetComponentTransform());
const float Scale = kTargetHeightCm / (Raw.BoxExtent.Z * 2.0f);   // ★ 用「高」这个可核对的量来标定
Body->SetRelativeScale3D(FVector(Scale));
const FBoxSphereBounds Fit = Body->CalcBounds(Body->GetComponentTransform());
// ★ 再把 (Fit.Origin.Z - Fit.BoxExtent.Z) 这个脚底世界 z 压到胶囊底部
```

★ **落地判据**：★ 把 **原始高 / 算出的缩放 / 实高 / 脚底 z / 地面 z** 打进一条日志 ——
★ 一行就能看出「悬空 / 陷地 / 巨人」，★ 比事后截图发现脚在地下早一整轮。

### ② ★★ **朝向不要推导，★ 用两帧实拍定死**

★ 实测：★ 源文件里的「模型朝前」**与引擎的轴约定不一致**，★ 而 ★ **两次按坐标系推出来的答案都被实拍否掉**
（★ 推出来那个 0° 显示成**侧面**、★ 90° 显示成**正对镜头**，★ 真正对的是另一个 90°）。

★ **做法**：★ 挂上 → 截一帧 → 认「正面 / 背面 / 侧面」→ ★ 加 90° 再截 → ★ **两帧就能定死偏移角**，
★ 然后把那个数写成常量、★ **并注明它是怎么来的**（★ 否则下一个人一定会"顺手修正"它）。

★ **判据**：★ **朝向问题看像素**（★ 与 `04 §4·14` 「朝向别靠推导」同族）。

### ③ ★★ 「模型进来了」≠「角色能用了」——★ 没有动画就是 A-pose

★ 外部源文件常常**只有骨架、没有动画** ⇒ ★ 站着像样、★ **一走路就是张臂 A-pose**。
★ **口径**：★ 交付时**显式写明「没有走路动画」** —— ★ 别让它混在"换模型完成"里成为假绿的一部分。
★ 补齐是另外两件事：★ 把动画源的骨架 **retarget** 过来 ＋ ★ 一个按速度驱动状态机的动画蓝图。

### ④ ★ 挂上骨骼网格后的三条收尾约定

| 项 | 设成 | 为什么 |
|---|---|---|
| ★ 该组件的碰撞 | ★ **关闭**（★ 角色另有胶囊负责碰撞） | ★ 两份碰撞会互相挡，★ 还会把「穿模」变成「卡住」 |
| ★ 影响导航 | ★ **关** | ★ 装饰性的身体不该改写寻路网格 |
| ★ 那张骨架资产的名字 | ★ **记进文档** | ★ 后面 retarget 一定要它，★ 到时候再翻就晚了 |

### ⑤ ★★ 无头 Python 侧：**属性名一律先探测，★ 不许凭记忆写**

★ 引擎暴露给脚本的属性名**与 C++ 里的名字不是一套**，★ 且**不同版本会改名**。★ 实测栽过的四类：

| 凭记忆写的那个 | 实际 | 后果 |
|---|---|---|
| ★ 导入选项里的「统一缩放」属性 | ★ 该版本的这个类**根本没有它** | ★ 脚本 `AttributeError` 当场崩 |
| ★ 导入任务的「状态」属性 | ★ 不存在 | ★ 想读回结果 ⇒ ★ 只能改用「资产在不在」当判据 |
| ★ 用「资产是否存在」判**目录** | ★ 实测：★ 判**目录**时它返回**假**（★ 那个 API 只对「资产」成立） | ★★ **会把「导入成功」报成「导入失败」**（★ 判目录要用另一条「目录是否存在」） |
| ★ 贴图尺寸 / 网格材质列表的字段名 | ★ 随版本不同 | ★ 读不到就崩整批 ⇒ ★ **必须守卫** |

★ **两条做法**：

1. ★ **探测优先**：★ 先把那个类的属性名全部打出来（★ `dir(类)`）再决定设哪些；
   ★ 并写一个 `setopt(obj, name, value)`：**有则设、无则记一条日志继续**
   ⇒ ★ **一个属性名不存在，★ 不拖垮整批导入。**
2. ★ **判据落在「产物」上，不落在「任务返回值」上**：★ 导入成不成，★ 看
   ★ **目标资产 / 目录在不在、包围盒读数对不对**，★ 不看「跑完了没报错」。

★ ★ **这一条与本文 §3·5·2「写完必须读回来」、`04 §4·8`「调用返回成功 ≠ 做成了」是同一条纪律的三个化身。**

## ★★★ `CanvasPanelSlot` 的"位置/尺寸"**不看锚点**（★ 读引擎源码定的，不是推导）

★ 场景：脚本化投递 UMG 布局时，想知道"读回来的 `Position`/`Size` 到底是不是屏幕上那块矩形"。

★ 源码（`Runtime/UMG/Private/Components/CanvasPanelSlot.cpp`）：

| 函数 | 实际做的事 |
|---|---|
| `SetPosition(X,Y)` | `Offsets.Left = X; Offsets.Top = Y` —— ★ 原样写 |
| `SetSize(X,Y)` | `Offsets.Right = X; Offsets.Bottom = Y` —— ★ 原样写 |
| `GetSize()` | `return (Offsets.Right, Offsets.Bottom)` —— ★ 原样读 |
| `GetPosition()` | `return (Offsets.Left, Offsets.Top)` |

★★ **结论**：这四个访问器**完全不看 `Anchors`**。所以

· 单点锚下 `(Right,Bottom)` 语义 = 宽高；★ 拉伸锚下 = 离父右/下边的**边距** —— ★ 语义随锚变，
· 但**数值层面它就是那两个字段本身** ⇒ ★ 拿"读回的 Position/Size"去对"写入的 Offsets"，
  ★ **两种锚都成立**，★ 不需要为拉伸锚开例外。
· ⇒ 判据：**写校验脚本时别因为"语义不同"就跳过一类控件**（★ 跳过的那一类正是漏检的那一类）。
  ★ 要跳过也得说清"跳过的同时漏掉了什么"，★ 并给这一类补一条**反向用例**。

★ 顺带：`SetLayout(FAnchorData)` 是**整包替换**（Offsets + Anchors + Alignment 一起），
★ 而 `SetPosition/SetSize` 只动 Offsets ⇒ ★ 增量"只补几何"的工具**不会补锚点** ——
★ 新建的拉伸锚件会停在默认 `(0,0,0,0)`，★ 于是"铺满父件"。⇒ ★ 补几何必须连锚点一起补。

## ★★★ `UButton` 的灰底：幽灵样式配方（★ 两个 API 名坑 + 一条"透明不等于不画"）

★ 症状：画稿里"只有文字"的按钮（页签、返回、链接式入口），实机全部画成**灰色圆角块**。
★ 根因：`UButton` 的 `Style` 默认值 = 引擎核心样式的 `Button` ⇒ ★ **不显式改就有底板**。

★★ 配方（★ 三处都是踩过才写下来的）：

```cpp
static const FButtonStyle& Ghost()
{
    static const FButtonStyle S = [] {
        FButtonStyle T;
        // ① 字段名是 **DrawAs**，★ 没有叫 DrawType 的字段（`GetDrawType()` 只是访问器）
        T.Normal.DrawAs   = ESlateBrushDrawType::NoDrawType;
        T.Hovered.DrawAs  = ESlateBrushDrawType::NoDrawType;
        T.Pressed.DrawAs  = ESlateBrushDrawType::NoDrawType;
        T.Disabled.DrawAs = ESlateBrushDrawType::NoDrawType;
        T.NormalPadding = FMargin(0.f);      // ③ 不清 ⇒ 文字整体偏移，★ 而读回 slot 几何看不见这个偏移
        T.PressedPadding = FMargin(0.f);
        return T;
    }();
    return S;
}
Btn->SetStyle(Ghost());   // ② UE 5.2 起 `SetStyle(const FButtonStyle&)` 收【引用】，★ 传指针编译不过
```

1. ★ **只把 `TintColor` 调透明不够** —— `DrawAs` 仍是 `Image` 时，空 Brush 画的是**纯色填充**
   （★ 本篇前面那节「空 Brush 的 `UImage` 会画成一块纯色」是同一条）。★ 必须 `NoDrawType`。
2. ★ `SetStyle` 5.2 起收**引用**（内部会拷贝）⇒ 样式对象**不必**活得比按钮久；
   ★ 但别的文本类控件的 `SetStyle` 有收**指针**的分支 ⇒ ★ 别照抄，★ 看那个类自己的头文件。
3. ★ 默认样式带 `NormalPadding` ⇒ 抹了灰底**文字还会偏移**；★ 而"读回的 slot 位置"是对的，
   ★ 所以这种偏移**只有像素能发现**。

## ★★★ UMG 的**树序就是 z 序**：装饰件排在交互件后面 = 盖住它并**吃掉点击**，★ 且日志零线索

★ 症状：按钮点了**毫无反应** —— 注入返回 `true`、画面不变、**日志里一个字都没有**。
★ 根因：`CanvasPanel` 在同一 `ZOrder` 下**按子节点顺序绘制**，★ 后建的画在上面；
★ 而 `UImage` / `UBorder` 默认 `Visible` ⇒ ★ **参与命中测试**。
⇒ 一块"给按钮当底板"的 Border 若排在按钮**之后**，★ 它就把按钮整块盖住，★ 点的全是底板。

★★ 两条对策（★ 一起做才稳）：
1. **顺序**：衬托某交互件的装饰件，★ 必须排在它**之前**；★ 并在生成表里注明"这条顺序有含义"，
   ★ 否则下一个加件的人只会按 DOM/清单顺序往下追加。
2. **命中**：装饰件设 `ESlateVisibility::HitTestInvisible` —— ★ 只靠顺序是脆的（★ 谁再插一条就复活）。

★ 判据：**"点了没反应"要拿日志证伪，不能拿事件注入的返回值作证** ——
★ 后者只代表"事件送进去了"，★ 不代表"送对了控件"。★ 本条正是靠"日志里没有预期那一行"定位的。
