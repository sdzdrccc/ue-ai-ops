### 2.2 ★★ 官方直接写出了「今天踩的那个坑」

★ `UMGToolSet` 的描述原文（★ 官方自己写的）：

> **重要工作流** —— 对于此工具集返回的每个控件和插槽：
> 1. 调用 `ObjectTools.list_properties(widget)` 以**发现确切的属性名称**
> 2. 使用这些确切的名称调用 `ObjectTools.get_properties(widget, [...])`
> 3. 使用这些确切的名称调用 `ObjectTools.set_properties(widget, {...})`
>
> **属性名称因控件类而异，无法猜测** —— 需要 `list_properties`。
> ★ **跳过步骤 1 会导致 `set_properties` 静默失败或设置错误的属性。**

★★ **这与实测经验完全一致** ⇒ ★ **「先发现、再读写」是官方强制的正确姿势**，
★ **「猜属性名」正是静默失败的来源**。

### 2.3 ★★ 「改 → 编译 → 单独保存」是**官方设计**（★ 重要更正）

★ `CompileWidgetBlueprint` 的描述原文：

> 编译一个控件蓝图。…**在所有控件和属性设置完毕后调用**。★ **通过 `AssetTools.save_asset` 单独保存。**

★★ **所以「写入后不会自动落盘」不是第三方插件的缺陷，而是官方有意为之** ——
★ **「编译」与「持久化」是两个独立步骤**（★ 批量改完再存更合理）。

> ★ **本报告更正了此前的一个判断**：
> 早前把「MCP 改资产不自动保存」当成某个第三方插件的 bug，
> ★ **实际这是这套体系的设计** ⇒ ★ **用官方工具时也必须显式 `save_asset`**。

### 2.4 ★★ `GetWidgets` 的能力（★ 比第三方强）

★ 实测返回（★ 关键字段）：

| 字段 | 值（实测） | ★ 意义 |
|---|---|---|
| ★ `parentClass` | ★ **`/Script/<项目名>.<OurUserWidget>`** | ★ **能确认 WBP 的 C++ 父类** —— ★ 第三方工具不返回这个 |
| `rootWidgetClass` | `VerticalBox` | 根控件类型 |
| `widgetCount` | ★ **43** | 控件总数 |
| ★ `inheritedWidgetCount` | ★ **30** | ★ **继承自 C++ 基类的控件数** |
| ★ 每个控件的 `bInherited` | ★ 逐项标注 | ★ **能直接看出「这个控件是 C++ 声明的」还是「WBP 里新加的」** |
| ★ 每个控件的 `slot` | ★ 如 `<...>.CardBox.VerticalBoxSlot_9` | ★ **精确到 slot 的引用** ⇒ 可**直接拿去读写插槽属性** |
| ★ `bIsVariable` | 如输入框/按钮为 `true` | ★ **能看出哪些暴露成了蓝图变量** |

★★ **对比结论**：★ **第三方工具给的是「名字 + 缩进」**；
★ **官方给的是「结构化对象图 + 继承来源 + slot 引用」** ⇒
★ **后者能直接驱动后续的属性读写，不必再解析文本。**

★ **实测还顺带验证了一件旧事**：★ 一个此前用**第三方**工具新建的控件
★ **确实出现在官方读出的树里** ⇒ ★ **它当时是真落盘了的**（★ 与 `02/03` 篇的结论一致）。

## 3. ★ 实测中发现的用法要点（★ 官方工具特有）

| # | 要点 | 说明 |
|---|---|---|
| 1 | ★ **引用用 `{"refPath": "…"}` 传递** | ★ 对象/类不是字符串，而是**软路径引用对象** ⇒ ★ 返回值可直接回传 |
| 2 | ★ **`call_tool` 的 `tool_name` 要去掉工具集前缀** | ★ 用短名（★ 带全名会报 `Unknown tool`） |
| 3 | ★ **必须「先发现、再读写」** | ★ 见 §2.2 —— ★ **猜名字 = 静默失败** |
| 4 | ★ **改完要 `CompileWidgetBlueprint` + `save_asset`** | ★ 见 §2.3 |
| 5 | ★ **`save_asset` 在 `AssetTools` 里** | ★ **不在 UMG 工具集里** ⇒ 跨工具集协作是常态 |
| 6 | ★ **服务端串行执行** | ★ 官方明确：**客户端不应发起重叠调用** |
