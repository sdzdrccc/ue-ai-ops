# 01 · 启动与编译

> ★ 全部结论来自**实测**（引擎 5.8 · Windows），★ 不是抄文档。
> ★ 凡具体路径都是**实例** ⇒ 换机器请用「怎么找」代替。

---

## 1. 找引擎

| 平台 | 位置 | 怎么确认版本 |
|---|---|---|
| Windows | `<安装根>/Engine/Binaries/Win64/UnrealEditor.exe` | 文件属性 / 启动后看标题栏 |
| macOS | `<安装根>/Engine/Binaries/Mac/UnrealEditor.app` | 同上 |

★ **认准「引擎根」的特征**：下面有 `Engine/Binaries/` 与 `Engine/Source/`。

★ **有没有 Launcher 是两回事**：
| 情况 | 表现 | 怎么办 |
|---|---|---|
| ★ **有 Launcher** | 能在界面里选工程 | 照常用 |
| ★ **只有引擎二进制**（无 Launcher / 无版本选择器） | ★ 双击 exe 会开★ **项目浏览器**，进不了工程 | ★ **必须命令行直启**（见下） |

★ **判别法**：★★ **双击 exe 后如果出现「选择工程」的窗口，说明没有 Launcher** ⇒ 以后都用命令行。

## 2. 启动

```bash
# ★ 通用形式（无 Launcher 时唯一可靠的路）
"<EngineRoot>/Engine/Binaries/Win64/UnrealEditor.exe" "<Project>/<Project>.uproject"
```

### 2.1 ★ 启动参数

| 参数 | 作用 |
|---|---|
| `-ModelContextProtocolStartServer` | ★ **让编辑器内的 MCP 服务自启**（见 `02-editor-mcp-channel.md`）· ★ **不带的代价见该篇** |

★ **其它可能有用的**（按需查引擎文档）：
| 参数 | 用途 |
|---|---|
| `-game` | 直接进游戏模式（跳过编辑器界面） |
| `-nullrhi` | 不渲染（省资源，用于纯逻辑跑测） |
| `-log` | 打开日志窗口 |
| `-nosplash` | 跳过启动画面 |

### 2.2 ★ 启动要等多久 / 怎么知道加载完了

| 阶段 | 现象 |
|---|---|
| 0–30 秒 | 进程起来，内存小 |
| ★ 30–180 秒 | ★ **内存持续上涨**（★ 着色器编译占大头）· ★ **这是正常的，别以为卡死** |
| 加载完 | 内存稳定在 GB 级 · 窗口可交互 |

★ **判据**：★ **看内存是否稳定**（Windows：`tasklist | findstr UnrealEditor` 看内存列）。

★ **首次启动某工程会更久**（要编译该工程的着色器），第二次起就快。

## 3. ★ 编译：三条路，先选对再动手

### 3.1 决策表

| 改动 | 走哪条路 |
|---|---|
| ★ **只改 `.cpp` 函数体** | ★ **热重载**（§3.2）—— 不关编辑器 |
| ★★ **改 `.h` 的反射**（`UPROPERTY` / `UCLASS` / `USTRUCT` / `UENUM`，★ **哪怕只改名**） | ★ **命令行全量编译**（§3.3）—— **必须关编辑器** |
| 改 `Build.cs` | 同上 |
| 改引擎源码 | 同上（且耗时显著变长） |

★ **一句话判据**：★ **这改动会不会让引擎需要重新生成反射信息（`.generated.h`）？会 ⇒ 全量编译。**

### 3.2 热重载（Live Coding）

| 项 | 值 |
|---|---|
| 快捷键 | ★ **`Ctrl+Alt+F11`**（★ 引擎硬编码的 "Compile shortcut"） |
| 出处（可自查） | `<Engine>/Source/Developer/Windows/LiveCodingServer/Private/External/LC_AppSettings.cpp` ★ 搜 `0x37A`（★ 0x37A = Ctrl+Alt+F11） |
| 自动编译开关 | ★ 同文件有 `continuous_compilation_enabled` |
| 启动日志 | ★ `Saved/Logs/<Project>.log` 里搜 `LogLiveCoding` ⇒ 出现 `Successfully initialized` 说明**已就绪** |

★ **怎么用**
```
1) 编辑器开着，改 .cpp
2) 焦点回到编辑器窗口 → Ctrl+Alt+F11
3) 看编辑器输出/右下角的编译状态
```

★ **它做不到的**：★ **任何让反射系统变化的改动** —— ★ 表现为「热重载报错 / 提示需要重启 / 改完不生效」。

### 3.3 命令行全量编译

```bash
# Windows
"<EngineRoot>/Engine/Build/BatchFiles/Build.bat" <TargetName> <Platform> <Config> -Project="<Project>/<Project>.uproject" -WaitMutex
```

| 参数位 | 常见值（★ 以你的 `.Target.cs` 为准） |
|---|---|
| TargetName | ★ 通常是 `<ProjectName>Editor`（编辑器目标）或 `<ProjectName>`（游戏目标） |
| Platform | ★ `Win64` / `Linux` / `Mac` |
| Config | ★ `Development` / `Debug` / `Shipping`（★ **`DebugGame` 也常见**） |

★ **常见坑**：
| 现象 | 原因 | 正解 |
|---|---|---|
| ★ 报 `Unable to build while Live Coding is active` | ★ **编辑器还开着** | ★ **关掉编辑器**（★ 消息里那句 "or press Ctrl+Alt+F11" 就是另一条路） |
| ★ 一个 `error C` 都没有但 `Result: Failed` | ★ **不是代码错** | ★ **看 `Result:` 那行措辞** |
| 输出被吞 / 看不到报错 | 管道用法问题 | ★ **重定向到文件再看**：`... > build.log 2>&1` |

★ **怎么找你的 TargetName**：
```bash
ls <Project>/Source/*.Target.cs
# 文件名去掉 .Target.cs 就是 TargetName（Editor / Game / Server 等变体）
```

### 3.4 ★★ 怎么确认「真的编过了」

★ **别只看「没报错」** —— 要看两样：
```bash
# ① 结果行
grep "Result:" build.log
#   期望：Result: Succeeded

# ② 产物时间戳比源码新（判据：比 .cpp 的修改时间新）
ls -la <Project>/Binaries/<Platform>/<Project>.dll
ls -la <Project>/Source/<Module>/<File>.cpp
```

★ **为什么**：★ **「命令跑了」≠「编过了」** —— ★ 内存/并发不足时可能中途失败而退出码仍是 0。

### 3·5 ★★★ 编得慢怎么办（★ 先量，再选手段）

★★ **先量再改** —— ★ 判据不是体感「又全量重编了」，而是**这次到底重编了几个编译单元**：

```bash
# ① 日志里 Compile 动作的行数（★ 最直接）
grep -c "\[.*\] Compile" build.log

# ② 改一个头之前，先数它被谁 include —— ★ 这个数就是「改它要重编的量」
grep -rl "<头文件名>" --include=*.cpp . | wc -l

# ③ 有没有走合并编译（★ UE5 的合并单元叫 Module.<模块名>.cpp，★ 不是 Unity_*.cpp）
find Intermediate -path "*<Module>/Module.*.cpp"
#    ★ 更快的判据：日志里出现 `Excluded from <Module> unity file: <文件>` ⇒ 合并编译正在跑
```

★★ **「改头就全量」最常见的来源就是合并编译（Unity）** ——
★ 启用时，模块里几十个 `.cpp` 被并成**一个**编译单元，★ **改任何一个头，那一个单元就整体重编**
⇒ ★ 体感正是「改一个头、等一整个模块」。

★ **小模块也会启用**：阈值（默认 **32**）算的是「自写 cpp ＋ UHT 生成的 `.gen.cpp`」——
★ 一个带 20 个 `UCLASS` 的模块，光生成的 `.gen.cpp` 就 20 个，★ 21 个 cpp 一加就过线。
★ **别拿「我的 cpp 不多」推断它没生效**，去找 `Module.<模块>.cpp`。

★ 另一类来源是**一个被十几个 `.cpp` include 的「枢纽头」** —— ★ 合并**没**启用时才按这个算。

**三个方向（★ 按持久性排序）**

| 方向 | 手段 | 收益 | 影响产物吗 |
|---|---|---|---|
| ① **少重编** | 砍头文件的影响面 | ★ 最持久 | ★ **不变**（只是编译单元变少） |
| ② **编得快** | 并行度 · 杀软白名单 · 别 clean | 立刻生效 | ★ **完全一致** |
| ③ **少重启** | 只改 `.cpp` 时走热重载 | 省掉最贵那段 | ★ 见 §3.1 决策表 |

**① 少重编 —— 目标是「改这个头，牵连几个 cpp」这个数字降下来**

1. ★★ **头里只留声明，重活搬 `.cpp`**：★ 若一个头为了几个函数而拖进重量级的引擎头（控件 / 字体 / 样式），
   把那些函数的**实现**搬进 `.cpp`，★ 头里只留 `Math/Color.h` 这一级的轻量头。
   ★ **调用点写法不用改**（`static` 成员函数改成普通静态成员，调用形式一样），★ 代价只是从内联变成一次函数调用。
2. ★ **前向声明替代 include**：`class UFoo;` ＋ `TObjectPtr<UFoo>`。
   ★ 但 ★ **返回值 / 成员「按值」持有完整类型时前向声明不够** —— 那是语言限制，
   ★ **别为了少重编把返回值改成指针**：改 API 的代价比多编几秒贵得多。
3. ★ **高频微调的常量挪出代码**（配置表 / ini）。
   ★★ 但 ★ **样式类常量别挪**：★ 挪出去 = **失去编译期检查**，写错键**静默取默认值** ——
   ★ 这种「不报错的失效」比编译慢危险一个量级。

**② 编得快 —— 零风险，但先认清哪些是默认**

| 手段 | 做法 | ★ 注意 |
|---|---|---|
| 并行度 | ★★ **默认别动**（`MaxParallelActions = 0` 表示自动） | ★★ 默认 0 会让 UBT 按「核数 ＋ **可用内存**」自己算（`GetMaxActionsToExecuteInParallel`），★ 且 `bAllCores` 默认 false ⇒ **只按物理核**。★ **手动设 N 是覆盖这套计算** —— ★ 除非「默认 vs 手设」对比实测说它算错了，否则别设 |
| 杀软实时扫描排除 | 工程目录 ＋ 引擎目录加白名单 | ★ **未量化**：收益随机器差异很大。★ 判据是**同一改动前后各跑一次比时间**，别信别人的百分比 |
| 只编需要的 Target | 日常迭代只编 Editor 变体 | ★★ **打包前必须单独编一次打包目标** —— `WITH_EDITOR` 分支在打包版里不存在，★ 这类差异会**攒到打包时才集中爆** |
| 别 clean / 别删 `Intermediate` | —— | ★ 见下条 |

★★ **`Intermediate` 是再生缓存** —— ★ 它**不是「不能删」**：★ 磁盘告急时它就是**第一顺位**。
★ 但要知道代价在哪儿：★ **引擎共享 PCH 的单个缓存文件可达 GB 级**（实测一份 2.5 GB），
★ 删它的真实成本是「**重编引擎 PCH**」，不是「重编你自己的模块」。
⇒ ★ **清它是拿时间换磁盘**，★ 别把它当「整理」在做。

★★ **这些默认值别去动**（★ 每条都能指到源码原文：`TargetRules.cs` / `ExecutorFactory.cs` / `UEBuildTarget.cs`；
★ 逐条台账在**源仓库** `docs/evidence/ubt-compile-speed-knobs.md` —— ★ 副本不含该目录）：

| 设置 | 默认 | ★ 别动它的理由 |
|---|---|---|
| `MinGameModuleSourceFilesForUnityBuild` | **32**（少于则强行关） | ★★ **别拿「我的 cpp 不多」推断它没生效**：计数含 UHT 生成的 `.gen.cpp` ⇒ ★ **UCLASS 多的模块很容易过线**。★ 真要确认就找 `Module.<模块>.cpp` |
| `bUseUnityBuild` | 生效（`IsUnity()` 对 Default 返 true） | ★ **关它未必更快**：合并单元少解析 N 遍头，但改一行就要重编整单元 ⇒ ★ **先量再决定**，别凭直觉关 |
| `bUseAdaptiveUnityBuild` | **开** | ★ 它专门把「近期频繁改的 .cpp」从合并单元里摘出来单独编 —— ★ 正是你要的效果，★ 别关 |
| `bUseIncrementalLinking` | **关** | ★★ 官方注释写明：某些机器上有 PDB 相关 bug ⇒ ★ **默认关是有原因的**，★ 别为了「更快」手动开 |
| UBA（Unreal Build Accelerator） | ★ **默认执行器** | ★ 不是可选项（源码注释 `We always use the UBA executor`）。★ 怀疑它作怪时用 `-NoUBA` **对照**排查，★ 不是常关 |

**③ 少重启 —— 最贵的那段往往不在编译上**

★ 改反射必须重启（§3.1），但**重启的代价** = 编辑器冷启动 ＋ 加载工程 ＋ 等着色器，
★ 常常比编译本身久。
- ★ 只改 `.cpp` ⇒ 编辑器内热重载（§3.2），全程不重启。
- ★ 必须重启 ⇒ 编译 → 启动一次。★ **别删 `DerivedDataCache`** —— 那会让着色器重编一遍。
- ★★ **热重载通过 ≠ 可以交付**：★ 热更**不重置**静态变量与单例状态，
  ★ 会出现「热更后正常、冷启动就崩」（或反过来） ⇒ ★ **里程碑 / 交付前必须冷启动验一次**。

**★★ 三条不许做的「提速」**

1. ★★ 把 `UPROPERTY` 降级成普通成员 ⇒ ★ **蓝图看不见 · 序列化失效 · GC 不追踪**。
2. ★ 为了少重编把 `UCLASS` / `USTRUCT` 拆成非反射结构。
3. ★ 频繁 clean「保持干净」—— ★ 那是**用最贵的代价换心理安慰**。

## 4. 完整流程（★ 改反射时的标准动作）

```
1) 停编辑器
2) 编译：Build.bat ... > build.log 2>&1
3) 验：grep "Result:" build.log   ⇒ 必须 Succeeded
4) 重开：UnrealEditor.exe <uproject> -ModelContextProtocolStartServer
5) 等加载完（看内存稳定）
```

★ **第 3 步不要省** —— ★ 省了就会在「跑起来才发现是旧 dll」上浪费更多时间。

## 6. ★★★ 启动前必做：**先确认有没有已经在跑的**

> ★★ **一条实测踩出来的硬纪律**（★ 不是建议）：
> ★ **启动编辑器之前，必须先查「有没有 UE 进程在跑」；有就先停掉，再启新的。**

### 6.1 ★ 为什么（★ 实测后果）

★ 实测：在**已有编辑器在跑**的情况下又启了一个 ⇒
★★ **两个进程争用同一份工程**（配置文件 · 日志文件 · 资产 · 派生数据缓存）⇒
★ **结果：崩溃报告器弹出、进程双双挂掉、日志互相覆盖、排查时看到的是错乱的时间线。**

★ 更隐蔽的后果：★ **日志被覆盖** ⇒ ★ **你看到的崩溃原因是另一个进程的**
⇒ ★★ **诊断会完全跑偏**（★ 本手册作者就为此浪费了一轮排查）。

### 6.2 ★ 正确姿势（★ 固化成三步）

```
① 查：有没有在跑的
② 停：有 ⇒ 先停干净（并等进程真的退出）
③ 启：确认进程数为 0，再启
```

★ **对应的命令（Windows）**：
```bash
# ① 查
tasklist | grep -i UnrealEditor

# ② 停（对每个 PID）
taskkill /PID <pid> /F
sleep 3 && tasklist | grep -ci UnrealEditor   # ★ 等它真的退出

# ③ 启（进程数为 0 之后）
"<EngineRoot>/Engine/Binaries/Win64/UnrealEditor.exe" "<Project>/<P>.uproject" -ModelContextProtocolStartServer
```

★ **判据**：★ **启动后进程数必须恰好是 1**。★ 若是 2 ⇒ ★ **立刻停一个**（★ 别留着）。

### 6.3 ★ 顺带：崩溃后要确认「真的退出了」

★ 实测：**崩溃后进程可能卡住不退出**（★ 日志已写「请求退出」，★ 但进程还在占内存）
⇒ ★ **必须显式检查并清理**，否则下次启动又变成「两个进程」。

### 6.4 ★ 一条相关提醒：**编辑器崩溃 ≠ 必是代码问题**

★ 实测：同一份代码可能因为**环境**而崩（★ 实测过「音频设备等不到 ⇒ 49 秒超时 ⇒ 崩」）。
★★ **定位方法：逐个变量隔离** ——
★ 先把可疑环境关掉（如 `-nosound` 禁音频），★ 再跑；★ 若还崩，★ **说明另有原因**。
★ **不要一崩就认定是刚改的代码**（★ 但也别排除 —— ★ 用隔离实验说话）。

## 7. ★★ 别把「常驻 GUI 程序」放进后台任务

★ 这一条是**踩过并实测确认**的，★ 属于 AI 客户端侧的通用坑，★ 不限编辑器。

### 7·1 ★ 现象：任务「一直运行中」，但其实什么都没在干

★ 实测：AI 用**后台模式**启动编辑器 ⇒ ★ 客户端出现一条永久「运行中」的任务。

★ **判据（★ 一眼识破）**：★ **拿「任务已运行时长」和「进程启动时刻」对时**。
```
「已运行 28m45s」+ 当前 16:39:25  ⇒  起于 16:10:40
编辑器进程 StartTime                =  16:10:35      ★ 差几秒 ⇒ ★ 就是它拉起来的
```

★★ **根因**：★ **后台任务等的是「命令退出」**，
★ 而 ★ **编辑器是常驻程序**（GUI 进程要人手动关）⇒ ★ **命令永不返回 ⇒ 任务永不结束**。

### 7·2 ★ 三类程序，只有一种该放后台

| 程序类型 | 例子 | ★ 该不该放后台 |
|---|---|---|
| ★ **会自己结束** | 编译 · 渲染 · 批处理 | ✅ 放 |
| ★ **常驻服务**（要人关） | ★ **编辑器** · dev server · 监听端口的服务 | ★ ★ **放前台，起完就返回** |
| ★ **等待外部输入** | 交互式脚本 | ★ **放前台**，否则等于挂死 |

★ **一句话**：★ **后台任务适合「等它做完」，不适合「等它结束」。**

### 7·3 ★ 正确姿势：起完就返回，把 PID 交出去

```
★ 差：后台任务里跑「启动编辑器」⇒ ★ 任务挂到天荒地老
★ 好：★ 起进程 → ★ ★ 立刻返回 PID 与端口 → ★ 任务当场结束
        ⇒ 用户自己决定什么时候关
        ⇒ ★ 「进程还活着」这件事 ★ 由 PID 判据管，★ 不由任务状态管
```

★ **判据**：
| # | 判据 | 做法 |
|---|---|---|
| 1 | ★ **进程活着 ≠ 任务在跑** | ★ 用 **PID + 端口/句柄**判断活性（→ `02-editor-mcp-channel.md` §2） |
| 2 | ★ **别用任务状态回答「程序在不在」** | ★ 任务状态管的是「命令退没退」，★ 与进程存活无关 |
| 3 | ★ **别让人去猜那条提示什么意思** | ★ ★ **起常驻进程时明确说一句「它会一直在，关编辑器即结束」** |

★★ **元纪律（★ 这条的真正价值）**：
> ★ **AI 自己起的进程，要对它的「生命周期表现」负责** ——
> ★ 让用户面对一条永久转圈的提示却不知道为什么，★ 是**遗留了沟通成本**，★ 不是「运行正常」。

## 8. ★★ 编辑器外的两条脚本通道（★ 与编辑器互斥）

> ★ 什么时候翻这节：★ **要跑一次性的批处理**（改资产 / 导数据 / 量东西），★ 而不是在编辑器里点。

### 8·1 ★ `-ExecutePythonScript`：跑完编辑器自己退出

★ **实测行为**：带这个开关启动 ⇒ 脚本跑完 **编辑器自己退出**（不是留在那儿）。
★ **想让它留着**：`unreal.EditorPythonScripting.set_keep_python_script_alive(True)` ——
★ **类名是 `EditorPythonScripting`**（★ 不是 `EditorPythonScriptingLibrary`，猜错直接 AttributeError）。

★★ **代价（★ 比"留着"这个好处重要）**：那个「正在执行 Python 脚本」的**异步任务通知**，
★ 只在执行器**请求退出**时才销毁 ⇒ ★ 开了 keep-alive 它就会**一直挂着**；
★ 而框上的「取消」**等于关编辑器**（不是取消脚本）。

★ **判据**：
1. ★ **要留就接受"一条常驻提示"**，并**提前告诉用户它是什么、怎么才会消失** ——
   ★ 否则对方会以为脚本卡住了（同 §7 的元纪律）；
2. ★ **一次性任务优先让它自己退出**（不设 keep-alive），★ 不留尾巴。

### 8·2 ★★ `-run=pythonscript`：commandlet 形态

```bash
<引擎>/Engine/Binaries/Win64/UnrealEditor-Cmd.exe "<工程>.uproject" \
  -run=pythonscript -script="<脚本>.py" -unattended -nosplash -nullrhi
```

★★ **与编辑器互斥**：★ **编辑器开着时跑必失败**（工程被锁）⇒
★ 先按 §6 确认进程数为 0 → 跑 → 跑完再起编辑器。

★★ **日志只认 `log_warning`**：commandlet 下 `unreal.log()` **不进日志**，
★ 只有 `unreal.log_warning()` / `unreal.log_error()` 进。
⇒ ★ **探针脚本一律用 warning**，否则整轮"跑成功了，但什么都看不到"（★ 症状与 §4·8 的静默失败同族）。

### 8·3 ★★ 编译卡死：判据是**产物时间戳**，不是「命令还没返回」

★ **实测**：`Build.bat` 偶发卡死在**一个编译单元**上 —— `cl.exe` 吃约 1GB 内存、
★ 十几分钟不动、日志一行不推进。

★ **处置**（★ 顺序固定）：
```bash
cmd //c "taskkill /IM cl.exe /F"     # 杀编译进程
cmd //c "taskkill /IM dotnet.exe /F" # 杀 UBT（它等 cl，会一起僵着）
# 然后原命令重跑一次 ⇒ 实测即过
```
★★ **判据**：**看 DLL / 可执行产物的 mtime 有没有变** ——
★ 变了 ⇒ 在推进（再等等）；★ 没变 ⇒ 已经僵死（别等）。
★ **"命令没返回"什么都不能证明**（同 §4·17：后台任务状态也不是判据）。

★★ **另一支卡死：UBA detour**（★ 症状不同，**别按上面那套治**）

| | 上面那支（cl.exe 卡） | ★ 这一支（UBA detour 卡） |
|---|---|---|
| ★ 症状 | `cl.exe` 吃 ~1 GB 内存、日志一行不推进 | ★ 日志打完 `Using Unreal Build Accelerator local executor to run N action(s)` **之后十分钟零输出**，★ **`cl.exe` 压根没起来** |
| ★ 判据 | 产物 mtime 不动 | ★ 同上，★ 但"没起 cl"是关键区别 |
| ★ 处置 | 杀 `cl` ＋ `dotnet` 后原样重跑 | ★★ **原命令加 `-NoUBA`** |

★ **实测**：两次卡死（一次 17 分钟、一次 4 分钟零进展），★ 加 `-NoUBA` 后 **2 分 9 秒** `Result: Succeeded`。

★★ **别把 `-NoUBA` 理解成「换了个执行器」** —— ★ 抬头照样打
`Using Unreal Build Accelerator local executor`，每个动作只标 `[NoUba]`：
★ **它禁的是 detour（劫持注入），不是执行器本身。**

### 8·4 ★ 热重载怎么触发：**快捷键注入不生效**

★ `LiveCoding.Compile` / `LiveCoding.CompileSync` 是**存在的控制台命令**。
★ 但 `PressKey("Ctrl+Alt+F11")` **打不上** —— ★ 热键由**外部 `LiveCodingConsole` 进程**注册，
★ Slate 层注入不触发它。

★ **两条可行路**：① 打开编辑器控制台敲 `LiveCoding.Compile`；② 关编辑器走命令行全量编译（§3.3）。
★ **来源**：实测（注入回执正常、编译没发生，改用控制台命令后当场生效）。

### 8·5 ★ 在 Git Bash 里驱动这些命令的两个坑

| 坑 | 症状 | 正解 |
|---|---|---|
| ★ `taskkill /IM xxx` 的参数被当**路径**做转义 | 报「无效参数 '<git 安装目录>/IM'」 | ★ 套一层：`cmd //c "taskkill /IM xxx /F"` |
| ★ `/tmp` 与 Windows 工具**不互通** | Git Bash 的 `/tmp` 实际映射到 Windows 的 `%LOCALAPPDATA%\Temp` ⇒ 脚本写 `/tmp/x.json` 后，下一个工具按自己的路径找不到 | ★ **跨工具传文件一律写明确的 Windows 路径**（别用 `/tmp`） |

★ **元判据**：★ **在 Git Bash 里调 Windows 原生程序，凡是"路径样式"的参数都要怀疑一次** ——
★ `/IM`、`/F`、`/PID` 这类开关长得像路径，就会被 MSYS 的路径转换改掉。
